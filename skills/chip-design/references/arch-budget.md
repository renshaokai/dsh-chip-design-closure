# 架构与预算

## 1. 先锁边界参数

架构设计开始前必须有这七个数，缺一项就问，不要默认：

| 参数 | 含义 | 典型追问 |
|---|---|---|
| 目标算力 / 吞吐 | TOPS、GOP/s、包速率、像素率 | 峰值还是有效值？ |
| 带宽 | 片外 GB/s、片上 byte/cycle | 读多还是写多？突发长度？ |
| 延迟 | 端到端 cycle 或 us | 平均还是最坏？ |
| 精度与数据格式 | INT8/FP16/BF16、描述符格式 | 是否要混合精度？ |
| 目标频率 | MHz（须注明工艺与库） | 典型 corner 还是 worst case？ |
| 面积/功耗预算 | mm²、mW | 动态还是含漏电？ |
| 接口约束 | AXI 位宽、outstanding、时钟域 | 主机是谁？需不需要 coherency？ |

## 2. 核心预算公式

**带宽**
```
片上带宽 (byte/cycle) = Σ(每周期读字节 + 每周期写字节)
片外带宽 (GB/s)      = byte/cycle × f(MHz) × 1e-3
有效带宽             = 理论带宽 × 访问效率
  访问效率 ≈ (1 - 冲突率) × (1 - 握手气泡率) × 突发利用率
```

**算力**
```
MAC 吞吐 (MAC/cycle) = PE 数 × 每 PE MAC 数
峰值算力 (GOPS)      = MAC/cycle × 2 × f(MHz) × 1e-3
有效算力             = 峰值 × 阵列利用率 × 数据复用效率
阵列利用率 ≈ 有效计算周期 / 总周期（含填充、边界、气泡）
```

**存储**
```
SRAM 容量 (bit) = 深度 × 位宽 × bank 数
SRAM 面积粗估   = 容量(bit) / 该节点 bit 密度（查工艺库，不要猜）
单口/双口 SRAM 的 cycle 吞吐差：单口读写互斥，双口可同拍
```

**卷积类负载的复用**
```
输入复用倍数 = 输出通道分块 × 卷积核面积
权重复用倍数 = 输出像素分块（feature map tile 面积）
总 DRAM 流量 ≈ 输入 + 权重 + 输出，均按 tile 边界向上取整后计入重复搬运
```

**流水线**
```
吞吐 = 1 / max(各级延迟, 反压造成的停顿)
延迟 = 级数 × 周期 + 握手开销
反压概率上升时，吞吐下降近似 = 吞吐 × (1 - stall_rate)
```

## 3. 从参数空间到权衡表

三种方案的对比表是**结论的呈现**，不是探索过程。跳过后面的 3.1–3.3 直接拍三个方案，等于用专家经验抽样——抽到的那三个点之间比出来的"最优"，可能整个空间里都排不进前十。**多目标下不存在唯一最优，正确产物是一组互不支配的解，外加每解被什么约束卡住。**

### 3.1 扫什么：四个维度定生死

自由度很多，但绝大多数组合的差异被这四个维度主导。**只扫这四个，其余固定在典型值并标注**：

| 维度 | 取值档位 | 怎么定档位 | 卡住它的硬约束 |
|---|---|---|---|
| 并行度（PE 数 / 阵列宽 / 通道数） | 2 的幂，从目标算力的 1/4 到 4 倍，如 8 / 16 / 32 / 64 | 面积每翻倍算力翻倍、带宽同步翻倍，不可能只涨一项 | 面积预算、布线拥塞 |
| 目标频率 | 0.8× / 1.0× / 1.2× 目标值 | 与工艺库绑定，**必须注明节点与 corner** | 该节点综合可达上限（问后端或查同类设计） |
| 片上存储（SRAM 容量 / 分块） | 如 256K / 512K / 1M bit | 由复用倍数反推，不是先定容量再找用途 | SRAM 面积占预算的比例 |
| 数据复用粒度（tile 尺寸 / 缓冲深度） | 如 8×8 / 16×16 / 32×8 | 决定 DRAM 流量与片上容量的兑换率 | 片外带宽、片上容量 |

**全场点数先算出来**：4×3×3×3 = 108 点。这个数决定能不能穷举——**百点以内穷举，上千点先粗后细**（见 3.2）。

**不要扫的**：流水级数（由频率与逻辑深度决定，不是自由变量）、接口位宽（通常被 SoC 协议锁死）、精度（需求给定）。把它们当自由度，扫出来的"最优"是在改需求，不是在选架构。

### 3.2 搜索与剪枝：先砍硬约束，再谈优劣

顺序错了会白算：**先用硬约束淘汰，再对幸存者算分数**。反过来先算综合分再排序，会让一堆本就不可行的点在榜首。

剪枝判据（任一命中，整支砍掉，不必算完）：
- 片外带宽需求 > 接口能力（如 LPDDR4-3200 × 32bit ≈ 25.6 GB/s）
- SRAM 面积 > 总面积预算的 50%（超过就说明架构在拿存储换算力，先质疑这个方向）
- 目标频率 > 该节点同类设计的可达上限
- 关键路径逻辑级数 > 该频率下的门级预算（用 `f × 门延迟` 粗估，别用"应该能跑"）

**粗后细（全场点上千时）**：
1. 每个维度做单维扫描，其余固定在中位值 —— 看斜率。**斜率最陡的那一维才是主战场**，人力往这里投。
2. 在斜率最陡的两维上做二维网格，其余固定 —— 通常就能看出 Pareto 形状。
3. 只对前沿附近的点补全其余维度。

**单维斜率比绝对值有用**。绝对值受模型误差影响（见 3.4），斜率的符号和量级基本靠得住："PE 从 16 加到 32，有效算力只涨 12%" 这个结论，即使模型差 30% 也仍然成立——它告诉你瓶颈不在算力。

### 3.3 输出 Pareto 前沿，不输出"最优方案"

解 A **支配**解 B，当且仅当 A 在所有目标上不差于 B、且至少一项严格更好。不被任何解支配的解构成前沿。

| 解 | 并行度 / 频率 / 存储 / tile | 有效算力 | 面积 | 功耗 | **被什么卡住** | 适用条件 |
|---|---|---|---|---|---|---|
| P1 | 8 / 1.0G / 256K / 8×8 | 低 | 最小 | 最低 | 片外带宽（复用不足） | 面积或功耗刚性约束、算力有余量 |
| P2 | 16 / 1.0G / 512K / 16×16 | 中 | 中 | 中 | 无单一瓶颈 | 通用场景，接口与面积都留了余量 |
| P3 | 32 / 1.0G / 1M / 32×8 | 高 | 大 | 高 | 片外带宽（32 宽已喂不饱） | 算力优先，且能配更宽接口 |

**"被什么卡住"这一列是这张表真正的价值**，不是算力数字。如果前沿上所有解都被同一个约束卡住（比如全是带宽受限），那优化方向就唯一了——**去改接口或改复用策略，不要再调阵列宽度**。看不到这一列，Pareto 前沿就只是一堆数字。

**三档结论，不给单一推荐**：面积优先取哪点、功耗优先取哪点、算力优先取哪点，各自一句话说明代价。多目标问题给单一"最优方案"，等于偷偷替用户定了权重。

### 3.4 模型精度的边界（必须写在表下）

解析模型只能排趋势、定量级，**不能替代综合与仿真**。表下固定写这句：

> 本表由解析模型（第 2 节公式）得出，误差量级 ±30%，用于**排序与剪枝**，不用于签核数字。定案前至少对 P1/P2/P3 三个点做一次综合或性能模型验证。

不做这一步就往下写 RTL，等于把一个 ±30% 的估计当成契约冻结——后期改动代价远高于先跑一次验证。

| PE 数 / 频率 | | | |

| SRAM 容量 | | | |

## 4. 架构决策台账（decisions）

每条决策三家话，缺一不可：

```
决策：卷积阵列采用 16×16 空间阵列，而非 8×8 + 双倍频率
备选：8×8@2GHz（面积小 30%，但频率难收敛，动态功耗高）
理由：目标频率 1GHz 下 16×16 即可满足算力，关键路径为 MAC 树 4 级，
      后端有余量；8×8 需 2GHz，触发器功耗上升明显
失效条件：若工艺降到低功耗节点、频率上限 800MHz，则算力不足，需改回双阵列
```

## 5. 面积与功耗的口径

- 面积三块分开报：逻辑（gate count 或 kGE）、SRAM（bit 数）、模拟/IO（个数）。混在一起没法比。
- 逻辑面积 ≈ gate count × 该节点单位门面积；组合逻辑与触发器比例影响功耗，不只影响面积。
- 动态功耗 ≈ α × C × V² × f，α 是每周期 0→1 翻转**概率**（口径与 `ppa-optimization.md` 第 1 节一致）；架构层面能改的是 α（复用、clock gating）和 C（并行度换频率）。
- 拿到的报告若给的是 toggle rate（每周期电平变化次数，0–2），换算成 α 时除以 2 再入公式，别直接代进去——这一步错了，功耗就报大一倍。
- **不给工艺节点就不要给绝对面积**。可以说"约为方案 A 的 1.4 倍"。
