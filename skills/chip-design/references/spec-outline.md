# 设计规格（Spec）骨架

八章骨架按「需求可追溯、契约可裁决」组织。裁剪必须在**第 1 章 1.3（行文规范与裁剪登记）**记原因——不登记就是缺章。

> **两套编号，别混**：`§1.x`（带 § 号）指本文件的「一、开工前」写作决策步骤；`1.x`（不带 §）指**文档模板的章节号**，与 `templates/spec-template.md` 一一对应。看到"在 1.3 登记"一律指模板第 1 章 1.3。

**排版前先做两个决定：文档分几份、往下拆到哪一层。** 这两件事定错，后面写得再细都是白费。

## 零、这份文档的双重身份

spec 当然描述设计——架构、接口、实现方式都在里面。但**描述不是它的第一属性，权威方向才是**。

| 身份 | 写在什么时候 | 冲突时谁服从谁 | 遇到不一致怎么办 |
|---|---|---|---|
| **契约** | 实现之前（至少 85% 评审时冻结） | 实现服从文档 | 先判是文档错还是代码错，改动走变更评审 |
| **记录 / 归档** | 实现之后（或同步补） | 文档服从实现 | 直接改文档，对齐代码 |

同一份文本可以两段时间分别承担两种身份：项目期间是契约，交付后成为归档参考。**但如果落笔的时间点在实现之后，它就只能是记录**——因为它必然与代码一致。而一份永远不可能和现实冲突的文档，无法用来检验现实是否正确。

**契约的全部价值来自它能被违反。** 能被证明为错的东西才能当标尺。一份只会描述"已经做成什么样"的文档，看着完整、看着专业，但它从来不指出任何问题，评审会上也没人能拿它说"这里不对"。

**自查判据：** 项目过程中，有没有人因为 spec 与自己想做的实现不一致，被迫改了设计或走了变更评审？如果从来没有，它不是契约，只是一份描述。

第 3 章、第 5 章写的内容确实是"设计长什么样"，但它们的生效方式不同——**它们是在实现存在之前写下来的约束，因此能反过来约束实现**。这不是文本差异，是时间点差异。

## 总则：形式先于内容

**这份文档有一类读者永远不读代码——验证工程师。** 对他而言，凡是可以被"你翻下代码就明白了"打发过去的地方，就是拿不到的信息。所以结论的**形式**不是排版偏好，它直接决定结论能不能被用。

### 0.1 三分工，各管一件事

| 形式 | 表达什么 | 特征 | 能否当证据 |
|---|---|---|---|
| **表** | 可核对的确定值：契约、状态、取值、条件组合 | 有编号有列名，每一格能被指着说"这里错了" | **能** |
| **图** | 关系与顺序：拓扑、数据流、拍级先后 | 一眼看出形状，看不出确切取值 | 看内容：承载值的图需配表，只表达结构的图本身就是完整证据 |
| **散文** | 只有"为什么"：决策理由、失效条件、边界说明 | 每节 ≤3 句 | 不能 |

判定一段文字该用哪种形式，问一句：**它有没有一组需要被逐条引用的值？** 有 → 表；只有形状和先后 → 图；只有缘由 → 散文。

**形式选对的标志是读者能据此做事**，不是"图比表好"或"表比图好"。同一个结论用错形式才需要改：结构说不清就用图画，取值说不明就用表列，理由讲不透就用散文。

### 0.2 三条技术规则

1. **表必带前提。** 行外假设写在表头或表上方（"以下均在 `cfg_mode=0`、`aclk` 单域下"）。写进正文段落的等于没有——表被单独引用时前提就丢了。
2. **承载值的图必须配表；只表达结构的图不必配。** 判据是：这张图能不能被指着说"这里错了"？
   - 能指出"第 3 拍的 `ready` 错了" → **必须有表**（时序图、波形图、状态机转移、计算映射的并行度与复用次数）
   - 只能看出"少了一条连线、层次画错了" → 图本身已是完整信息，**不要再造一张镜像表**
   波形图尤其不能只有图：只画波形、不列「拍号 / 信号 / 期望值 / 前提」四列，验证看着像对、照着写却对不上——因为波形图隐含了"读者已知当前配置"这个前提。
3. **散文有上限。** 解释性文字每节 ≤3 句。超了只有两种可能：该拆成表了，或者决策还没定——两种都该在评审时打回。

**这里是全篇唯一需要列外的地方：状态机的「跳转原理」（3.b）。** 它要回答四个问题（为什么这么划、为什么不合并、中间态为什么存在、瓶颈在哪），压到 3 句里必然丢东西。所以 3.b 放宽到 3–5 句，且**只此一处**——其余各节的散文一律 ≤3 句。写这段时按四个问题各一句组织，超出就是在复述跳转表。

| 节 | 散文上限 | 理由 |
|---|---|---|
| 绝大多数節 | ≤3 句 | 超过即该拆表，或决策未定 |
| 职责（六要素第 1 条） | 1 句 + 不做什么 | 边界必须用句子写，表写不出"不做什么" |
| **3.b 状态机跳转原理** | **3–5 句** | 四个问题各需一句，压缩即失真 |
| 其余部分 | 0 句 | 全是表、图、编号列表 |

### 0.2.1 图的三种落法，不要一律配表

| 关系 | 适用 | 做法 |
|---|---|---|
| **图为主，表是补充** | 结构图、层次图 | 表写的是图表达不了的另一维度（如"不做什么"、责任人），**不是把图的方框复述一遍** |
| **表为主，图是概览** | 时序、状态机、计算映射 | 表是权威，图帮读者先建立整体感觉；两者冲突时以表为准并回改图 |
| **只有图** | 纯拓扑、模块框图、数据流走向 | 图已是全部信息。此时配表 = 制造第二份手工维护的副本 |

**第三行必须允许存在。** 否则就与附录 A 的纪律自相矛盾——那里明令不许出现"两份手工维护的同一张表"，而逼着每张图配镜像表正是同一件事。**图和表不是一一对应，是各承担一种粒度。**

### 0.3 要禁的是这两种，不是散文

```
| 方案 | 理由 |          ← 反向错误：把理由切成碎片
| A    | 性能更好 |
```

理由天然是叙述性的，硬做成表只是填字游戏。真正要禁的是两头：

| 禁的 | 长什么样 | 危害 |
|---|---|---|
| **用散文（或图）代替取值** | "握手会在适当的时候反压一下""见图 3 便知" | 缺证据，谁也核对不了 |
| **追着图造镜像表** | 图上五个方框，就造五行表复述一遍 | 造冗余，两份数据要同步维护，必然漂移 |

中间地带是正常的：结构图配一张"职责 / 不做什么 / 责任人"表（表写的是图表达不了的维度），计算映射图配算子表（图给形状、表给并行度），都不算冗余。

**散文占篇幅超过三成的 spec，通常不是作者文笔好，而是契约还没形成。** 这一条是**观察信号，不是判据**——真正的判据是 0.2 的"每节 ≤3 句"。反过来也不成立：散文少不等于合格，可能只是把该讲理由的地方砍成了表。

### 0.4 四条判据（一条不满足就不算合格）

| 判据 | 问法 | 只满足它的文档长什么样 |
|---|---|---|
| **契约性** | 有没有人因为 spec 与实现不一致，被迫改了设计或走了变更评审？（见上文"零"） | 只有时序数字和寄存器表，没有"为什么" |
| **约束力** | 从文档能唯一推回实现方案吗？（见 0.6） | 决策清楚但缺背景，老手看得懂，新人看不懂 |
| **可交接** | 作者不在场时，这份文档还能被用起来吗？ | 面面俱到像教科书，但不知道从哪读起、改哪里会炸 |
| **可裁决** | 某一拍某信号该是 0 还是 1，能靠文档判决吗？ | 有描述没预期值，验证只能跑仿真反推、或去问作者 |

四条的读者依次是：评审人、实现者、接手者、验证者。**验证者最苛刻**——他不读代码，也没有作者可问；文档判不了，他的用例就在猜，猜错时有 50% 概率把正确的 RTL 判成缺陷，然后提一条"结果不一致"的记录，对设计侧毫无用处。

可裁决的表述要三要素齐全，缺一条就退化成猜测：

| 要素 | 不合格 | 合格 |
|---|---|---|
| 预期值 | "`ready` 应该会拉高" | "`ready` 在第 3 拍拉高" |
| 采样边沿 | "下一个周期" | "`aclk` 上升沿，`valid` 为高时采样" |
| 触发条件 | "正常传输时" | "`cfg_burst=1` 且 `len<8` 时" |

### 0.5 横向穷尽，纵向到决策

| 维度 | 含义 | 边界 |
|---|---|---|
| **横向**（覆盖面） | 功能、模式、异常路径、边界组合是否写全 | **没有上限，应当穷尽** |
| **纵向**（深度） | 同一功能从"做什么"写到"哪一拍哪个信号" | **止于决策层** |

纵向写到哪，是分水岭：

| 写什么 | 例子 | 写不写 |
|---|---|---|
| 决策 | 三级流水、并行度 16、双口 SRAM、round-robin 仲裁 | **必须写死** |
| 判定条件 | `valid` 拉高到 `ready` 拉高 ≤3 拍，超出即 fail | **必须写死** |
| 资源账 | 深度 512 × 32 bit × 2 bank，单口读写互斥 | **必须写死** |
| 精度口径 | 累加 32 位，截位到 8 位，饱和不舍入 | **必须写死** |
| 语句 | `if (cnt == 4'd7) state <= S_WAIT;` | 不写 |
| 风格 | 三段式还是两段式、信号前缀 | 不写 |

一条判据：**这条细节会不会影响别人？** 会影响集成方、验证方或后端 → 写死；只影响设计者自己怎么写 → 留给实现。

过度详细的代价是真实的：文档一旦写到语句层，实现遇到时序收敛不了或面积超了，团队会倾向"让实现将就文档"，而不是回去改方案——因为改文档要重新评审。**详细度越高，越需要配套的偏离登记纪律**（见 1.1.1）；只写不回写，详细就是负债。

### 0.6 三档：文档要能唯一推回实现方案

| 档 | 症状 |
|---|---|
| 太粗 | 两份完全不同的 RTL 都能满足同一份文档——约束不足，方案可被随意换掉 |
| **恰好** | 流水级数、并行度、存储组织、仲裁策略、状态划分都定了，代码怎么写只剩风格问题 |
| 太细 | 写到信号名、位选、if 嵌套顺序——成了代码抄本，评审等于读代码，且必然漂移 |

"恰好"这个位置就是**微架构决策层**。

### 0.7 一句自查

> **如果一份文档必须读代码才能判断方案是否合理，它就没承担起职责。**

主管只评审文档、不读代码，理由正在这里：**代码评审发现"写错了"，文档评审发现"想错了"。** 写错了改代码代价一天，想错了要重构架构代价一个月。三层各管一段，谁也替不了谁：

| 谁 | 看什么 | 判什么 |
|---|---|---|
| 主管 / 架构师 | 文档 | 方案对不对 |
| 设计者互查 | 代码 | 实现对不对 |
| 验证 | 波形与覆盖率 | 行为对不对 |

主管翻文档时实际在问四个问题，文档要能逐条答上：**能不能达标**（预算算式）、**有没有更简单的做法**（备选与失效条件）、**哪里会出问题**（关键路径 / 跨域 / 边界）、**出了问题查得出来吗**（状态寄存器与可观测出口，见第 3 章末）。第四条最常被漏，而它决定芯片回来后能不能调。

## 一、开工前：先分诊，再定粒度

> 本节小节号用 `§1.x` 标记，与第 1 章（文档信息）的 `1.1–1.6` 是两个命名空间：前者是动笔前的决策步骤，后者是文档模板里的章节号。全文引用遵循此约定。

### §1.0 先分诊：从用户说的话里读出他要什么

**不要把"要写哪种 spec"当问题抛给用户。** IP 规格 / 模块规格、架构级 / 实现级、正向 / 反向——这些标签都是后续几步（方向 §1.3、拆分 §1.1/§1.2、深度 0.6 与归档/交接档）的**推导结果**，不是入口处的选择题。

但推导的输入不是"资产清单"——**用户不会主动报"我有 RTL、无文档、无设计者可访谈、代码已冻结"**。他会说"帮我看看这个模块"并扔一个 `.sv`，或者"下周要交 spec"什么都不给。所以分诊的输入是**他怎么说 + 他给了什么**。

#### 第一步：读信号

| 用户怎么说 / 给了什么 | 已经能确定 | 真正还缺的 |
|---|---|---|
| 甩一个 `.sv`/`.v`/仓库路径，不说要什么 | 有 RTL，八成要文档或解释 | 给谁用（定档位）——**唯一该问的** |
| "这模块我看不懂 / 刚接手别人的 IP" | 反向 + **交接档** | 无。直接开工，别问 |
| "下周评审" / "要交付出去" | 正向契约，时间紧 → 先给骨架 | 评审范围、PRD 在哪 |
| "驱动 / 软件同事问我要寄存器" | 反向归档档，只要第 4/5 章 | 无。直接给摘录 |
| **"我想做个 XX"（还没有代码）** | **不是 B，是 A 分支**（先出架构方案） | 算力 / 频率目标，1–2 个 |
| "帮我补个文档"（什么都没给） | 只有意图 | 手上有什么——这条必须问 |
| 文档与代码都在，说"对不上" | 对账，先判哪边失效 | 文档是否还有效（他通常知道） |
| 只说"写个 spec"并给了 PRD | 正向，八章全填 | 交付时间与验收人 |

最后一行和第五行是最容易走错的：**只有想法没有 PRD 的，进 A 分支先出方案，不要进 B 要 PRD**——B 的输入就是 PRD，没有 PRD 就写不出第 2 章，硬写只能靠经验值编。

#### 第二步：能推的先推，推不出才问，且问不超过两个

真正推不出、不问就一定做错的只有三类：

| 必须问 | 为什么推不出 | 决定什么 |
|---|---|---|
| **交给谁验收**（评审会 / 验证 / 驱动 / 就自己看） | 只有用户知道 | 档位与等效于"契约还是记录" |
| **什么时候要** | 只有用户知道 | 详略与先给哪一章 |
| **他自己懂不懂这个模块** | 从"刚接手"能推一半 | "我写你审"还是"我先讲给你听" |

其余一律**先按最可能的假设填一版并标注假设**，让用户对着具体内容改口——看到一版带假设的目录，他补充得比回答八个问题快得多。缺五六个参数还在追问，是把用户当表格填。

#### 第三步：复述确认，不要默认对方跟你想的一样

推完之后用一句话把结论、依据、退路一起给出去，**让他只需要回"对"或"不是，其实……"**：

> 你给的是一个 `.sv`、没有文档、提到验证同事在等 → 我判断要的是 **as-built 交接档**（验证要拿它写用例，所以第 3 章要写到决策层）。我先把骨架和问题清单出来，你看方向对不对；如果其实只是给驱动看寄存器，说一声，我改成第 4/5 章摘录版。

格式固定三段：**结论 / 依据 / 退路**。没有"退路"那句，用户会被迫接受一个错误分类，而改口成本变高。

#### 第四步：在第一个里程碑上自检一次

开头的复述只能拦一次。如果用户回"好的继续"，推定就再没被检验过，**分类错了会一路错到交付**——而那时候推翻的成本已经是重写。

所以在**第一份可看的东西出现时**停一下：正向是骨架 + 前两三章，反向是问题清单 + 功能表候选。用一句问深浅对不对：

> 这三章的详略是按"给验证用"定的——第 3 章写到决策层、功能表带验收判据。对你的用途合适吗？如果只是给驱动看寄存器，后四章可以砍掉。

三条纪律：

- **只在第一个里程碑问一次**，不是每章都问——那是把确认变成打扰。
- **问"深浅和用途对不对"，不要问"这样写行不行"**。后者只会得到一声"行"；前者才可能换来"其实我要交的是集成，不用这么细"。
- **用户说"就这样"也要留书面依据**：文首那行"本版依据：用途 X、缺失 Y"照写。将来有人质疑详略，至少能查到当时是按什么定的。

判据是**产出可观、推翻成本还不高**的时刻——再晚一点，对齐就变成返工。各分支的第一个里程碑不同：A 分支在预算表出来后核"目标口径对不对"，B 在骨架 + 前两三章，B′ 在问题清单 + 功能表候选出来之后。

#### 资产与产出对照（推导表的速查版）

| 手头资产 | 用户缺什么 | 该产出 | 走哪条路 |
|---|---|---|---|
| 只有想法，连 PRD 都没有 | 方案本身 | 架构方案（预算 + 权衡表） | **A 分支**，不是 B |
| 需求 / PRD，无 RTL | 没想清怎么实现，评审没法过 | 正向设计文档（契约） | §1.3 正向 → 八章全填，B 分支 |
| 有 RTL，无文档 | 驱动 / 集成 / 验证在等交付依据 | as-built 记录 | §1.3 反向 → 第五节；档位按"敢不敢改代码"定 |
| 有 RTL，但读不懂（他人写的、接手的） | 理解与接手能力 | **交接档**：阅读路径、代码地图、3.a–3.d 写到决策层 | 反向 → 5.3 交接档 + 1.6 |
| 只要给驱动 / 集成一个参考 | 寄存器与端口说明 | as-built 摘录（第 4/5 章 + 附录 A/B），不写全文 | 反向 → 归档档裁剪 |
| 有文档，RTL 又改了 | 文档对不上代码 | 增量回填（diff 定界，只回填受影响章节） | 5.6 增量回填 |
| 有文档有 RTL，要加新功能 | 改动方案与影响面 | **先改文档再改代码**（文档驱动 + 偏离登记） | 正向流程作用于既有文档 |
| 文档与 RTL 互相矛盾，说不清谁对 | 一个"哪个是真的"的判决 | 先跑对账再定哪边让步：文档还有效 → 偏离处理；已失效 → 反向回填 | review-checklist「Spec ↔ RTL 对账」 |

**绝不许问的**："你要 IP 级还是模块级、架构级还是实现级？"——那是我们该替用户算出来的答案，问出来等于把分析工作退回给他。

两个常见误判对照：

- **把代码规模当拆分判据**（如"多模块超 5 个或 5000 行就建议写 IP 规格"）。行数大通常契约面也大，所以规模可当**提示信号**（回头查一下契约面是否值得拆），但不是判据——5000 行的纯流水复用契约面可能只有一张端口表，300 行的仲裁器可能值得单独成文。拆分只认 §1.1 责任边界四条与 §1.2 契约三判据。
- **把抽象层次当文档类别**（如"架构级 / 实现级"两套模板）。"架构级文档"实际是同一骨架下只填契约面章节、决策层章节空着并给理由——是 0.6 三档与"空章节三选一"的一种用法。做成两套独立文档，接口描述必然出现两份手工同步的副本，违反单一源纪律。

### §1.1 拆成多份文档，还是留在一份

| 判据 | 拆成独立文档 | 留在一份文档 |
|---|---|---|
| 责任人 | 有人独立负责这块，能自己交三次评审 | 同一个人的分工 |
| 交付节奏 | 可先冻结、先 release，不等其他人 | 必须一起冻结 |
| 评审场合 | 有独立的评审会与评审记录 | 跟随上级文档评审 |
| 版本演进 | 有自己的版本号，独立迭代 | 跟着上级版本走 |

**两条以上落在"拆"这一列 → 拆。** 只满足一条通常不值得拆——拆分成本（交叉引用维护、版本对齐、评审排队）往往大于收益。

**一个 IP 内部有几个子模块，不构成拆文档的理由。** 子模块是该 IP 的内部结构，不是独立交付物：它不是别人改的、没有独立版本号、不为它单开评审会。这种情况是**一份文档 + 章节分层**，不是多份文档。

### §1.2 往下拆到哪一层为止

**spec 的拆分粒度 ≠ RTL 的例化层级。** 这两者被混为一谈是文档臃肿的主因：RTL 里例化几十个 leaf module 很正常，spec 里可能只写五个模块。叶子模块是实现者的自由，不是契约——把 8 位移位寄存器写进 spec，等于替设计者做实现选择，还白占一页。

**满足任意一条 → 继续往下拆：**

| 判据 | 问法 |
|---|---|
| 有独立契约 | 它的接口会被别的模块或团队引用吗？改接口要走评审吗？ |
| 有独立验证环境 | 能单独建 testbench 跑覆盖率，还是必须整链才验得了？ |
| 有独立寄存器或时钟域 | 自己带寄存器吗？自己有时钟域/复位域吗？ |

**出现任意一条 → 停在这一层，不再往下：**

- 它变了，只需要通知写这段代码的那个人——那是实现细节，不是契约
- 它的接口是父模块内部的临时线，不出父模块边界
- 没有自己的寄存器、没有跨域，只是纯组合逻辑或纯流水切分

**一条经验值：三层基本够。** IP → 子模块 → 有契约的小模块。出现第四层时，通常不是设计复杂，而是有人把 RTL 结构图直接抄进了 spec——评审会问"这一层为什么需要单独写"，答不上来就是过度拆分。

### §1.3 先判方向：从需求写，还是从 RTL 反推

同一份八章骨架，有两个撰写方向，产出物的效力完全不同：

| | 正向（B 分支，plan） | 反向（B′ 分支，as-built） |
|---|---|---|
| 起点 | **PRD**（产品需求规格） | 已有 RTL |
| 实现状态 | 不存在或未冻结 | 已经完成 |
| 文档效力 | **契约**：实现服从文档 | **记录**：文档服从实现 |
| 冲突处理 | 改代码或走变更评审 | 改文档 |
| 主要读者 | 设计者、验证者 | 驱动/软件、集成、后来接手的人 |
| 八章覆盖 | 全部八章 | 2.2 / 3 / 4 / 5 / 6B 可写，2.1 与 7 章基本为空 |

**方向一旦是反向，就不能宣称它是契约。** 详细做法见第五节「逆向补文档」。

#### §1.3.1 正向的输入是 PRD，不是 MRD

三层需求文档各答一个问题，混用会让第 2 章写空：

| 层 | 文档 | 回答什么 | 对 spec 的贡献 |
|---|---|---|---|
| 立项 | **MRD**（市场需求文档） | 这颗芯片值不值得做、卖给谁 | 2.1 应用场景、目标客户、竞品对标、上市时间窗 |
| 产品 | **PRD**（产品需求规格，芯片行业也作产品规格需求书） | 做成什么样 | **2.2 功能列表、性能指标、接口形态、封装、功耗与成本预算、可靠性等级、验收判据** |
| 系统 | 系统需求规格 / 架构规格 | 怎么摊到子系统与模块 | 第 3 章预算参数的分配依据 |

**spec 要的硬约束几乎全部出自 PRD。** 拿 MRD 当输入，能写出的只有 2.1 场景描写——功能表没有条目、指标没有数字、分级无从判起。

**一条质量判据：PRD 只给功能清单、不给量化指标（吞吐 / 延迟 / 功耗上限 / 面积或成本上限）时，2.2 的分级就是设计者自己拍的。** P0/P1/P2 的判定标准是"缺了它模块能不能用"，而"够不够用"必须有数字才判得了。遇到这种情况，先把缺指标进缺口表并写明影响（FP 分级失去依据），不要用经验值补齐冒充 PRD 结论。

**MRD 不必删。** 反向回填时 5.2 里那四类（需求编号、验收判据、算法语义、取舍理由）分别落在 PRD 与 RTM 里，"为什么做这个功能"的依据则在 MRD——三条都指向同一件事：先确认手上是哪一份文档，再决定能写哪一章。**注意：这不改变"这些栏位必须给候选"的规矩**，只是说明候选该拿什么去对——写 `REQ-001（TBC）` 并指 `Q-03`，不是留空等 PRD。

一句话：**拆到"责任可交付、接口可冻结、验证可独立"为止，不拆到代码叶子。**

### §1.4 取证口径（两个方向都适用）

章节骨架两边通用，但**取证要求一致、出处不同**：

- **正向（契约）**：RTL 尚未存在，结论来自意图。出处是 PRD 条款编号、架构决策编号或协议条文。**引 PRD 时写条款号，不写"PRD 里说了"**——后者无法核对。
- **反向（记录）**：已有 RTL，回填文档。出处是源码。**凡 RTL 不能直接证明的时序、周期、容量，一律标推导，不得写成保证值。**

两条铁律：

1. **每个可验证结论都要有出处。** 出处是源码引用、协议章节号、PRD 条款号或架构决策编号；四者都没有的，进附录 E，不许留白也不许编。
2. **推导值不给保证。** 文中出现"最多 N 拍""深度 ≥ M""带宽约 X"这类数字，必须同句标明是推导还是保证，并写清推导前提。下游按保证值用，前提一变就出事。

证据分级三个标记，全文统一（正反向都用，反向强制每栏标）：

| 标记 | 含义 | 典型例子 |
|---|---|---|
| `measured` | 源码直接可读 / 决策直接给了数 | 赋值语句、位选、敏感列表、例化连接 |
| `inferred` | 由多处代码合理推出，无单点证明 | 协议类型、时钟域归属、模块职责边界、频率上限、跨域方案 |
| `TBC` | 已给候选，等一句话确认（**必指 `Q-xx`**） | `REQ-xxx` 候选、算法语义、取舍理由 |

**`tbd` 已从内容行废除。** 反向文档不许留空白（见第五节 5.2）——四类代码里读不出来的信息一律给候选标 `TBC` 并指问题编号，而不是标 `tbd` 留空。`tbd` 只在描述"历史上曾这样处理"时出现，不作为交付状态。

一个常见误判：**把 `inferred` 当 `measured` 交付。** 协议类型几乎永远是推的——RTL 里没有"这条是 AXI4"的声明，按信号后缀推断在 AXI 全/精简/A-Stream 之间最容易错。标成实测值，集成方按 AXI 语义接上去就出事。详见第五节 5.1。

## 二、八章骨架（单份文档通用）

### 第 1 章 文档信息

> 以下 `1.0–1.6` 是文档模板的章节号，与第一节的 `§1.x`（分诊与粒度决策步骤）不是一套编号。

- **1.0 文档控制**（编号 / 密级 / 状态 / 生效日期 / 主笔 / 复核 / 批准 / 分发范围 + 审批记录表）——这一节是给归档与审计用的，见 1.0.1
- 1.1 修订记录（版本 / 日期 / 作者 / 变更点 / **偏离登记** / 章责任人）——填写纪律见 1.1.1
- 1.2 术语与缩略语（硬件里同名不同义的东西太多，必须定义）
- **1.2.1 编号族总表**（十类编号的归属与复用规则）——见 1.2.2
- 1.3 行文规范与裁剪登记（裁了哪章、为什么、谁批准 + **规范性动词约定**）
- 1.4 参考文档（架构书、协议规范、相关 spec 版本号）
- 1.5 **下级文档索引**（仅当存在独立子文档时）——文档名 / 编号 / 版本 / 责任人 / 当前评审阶段，一眼看出哪份还没过 85%
- 1.6 **阅读路径与代码地图**（见 1.6 节）

#### 1.0.1 文档控制：为什么值得占一节

工程师会觉得"编号、密级、签发人"是仪式。**但在评审会上，评审组的第一句话通常是"这是哪一版、谁签的、什么密级"**——答不上来，后面讲什么都白讲。三件事必须有位置落笔：

| 项 | 不写的后果 |
|---|---|
| **密级** | 客户项目的内部文档被当成可外发材料，这是合规事故，不是文档缺陷。客户项目一律标"客户机密" |
| **审批记录** | 只有"主笔"没有"复核/批准"，等于这份文档没人认领。出问题时追不到人 |
| **分发范围** | 不知道谁能看，于是谁都在看，或者该看的人没拿到 |

**反向档的特殊处理**：批准栏通常空着，**如实写"待客户确认"而不是留空**——空着会被当漏填，写清状态才能表达"这份还没人认领"。这是两种完全不同的信号：前者是疏忽，后者是状态。

**"有条件通过"必须在结论列写出条件**，否则三个月后没人知道当时条件是什么，评审记录就成了一张废纸。

#### 1.2.2 编号族：为什么必须列一张总表

**一份规格里会同时存在十类编号**（`F-` / `FP-` / `VP-` / `Q-` / `A-` / `CPL-` / `INV-` / `D-` / `REQ-` / `L-`）。不列表的后果很具体：**同一个 `-01` 在三个地方指三样东西**，评审时双方各说各的编号，十分钟过去了还在确认"你说的是哪个 01"。

三条通用规矩，每一条都对应一种真实事故：

- **编号一经发出不许回收重用。** 删掉一条就把号空着。回收会导致历史版本与当前版本"同号不同物"——这是评审最难查的一类错，因为两边看到的东西都自洽。
- **引用只写编号，不重述内容。** 写 `见 CPL-01`，不写"见 CPL-01（done 宽度恰 1 拍）"。重述就会分叉，两处迟早不一致，而读者不知道信哪个。
- **编号前缀不跨文档借用。** 本项目 `Q-01` 与供应商文档的 `Q-01` 毫无关系。跨文档引用一律写全"文档编号 + 编号"，否则半年后没人分得清。

> **`REQ-` 是唯一一个编号不变但状态会变的族**（`TBC` → `已确认`）。这一条要写进总表，否则有人会把"确认后的需求"重新编一个新号，导致追溯矩阵里的旧引用全部失效。

#### 1.1.1 修订记录与偏离登记

文档写到决策层之后，RTL 实现阶段**一定会**有偏离：某个存储换成寄存器堆、某一级流水被合并、某个异常处理挪了位置。偏离本身都正常，**静默偏离是唯一不可接受的做法**。

| 做法 | 后果 |
|---|---|
| 改文档、升修订号 | 正常 |
| 文档里写"实现偏离 X，原因 Y，待下版合并" | 可接受，必须留痕 |
| 什么都不写 | **不可接受**——文档仍在被当有效规范引用，验证照它写用例会在正确的 RTL 上失败 |

修订记录要能回答两个问题：**哪次提交对应哪一版文档**（否则回溯时对不上）、**这一版改了什么导致下游要动什么**（否则验证不知道基线失效范围）。

已知过期但来不及改的章节，就地标 `⚠ 已过期，见 vX.Y`，不要留着当有效内容：**一份陈旧文档比没有文档更危险**——没有文档，新人知道自己不知道，会去读代码、去问人；有陈旧文档，他以为自己知道，错在根上，而作者可能已经不在。

另有两项纪律：

- **归属到章**：每章标责任人，不只全文一个。否则谁都不改。
- **触发式更新**：不是"定期更新"，是**接口、寄存器、状态机变化时必须更新**。这三样变了而文档没变，属缺陷。

#### 1.3.1 行文规范里的另一项：规范性动词

1.3 除了登记"裁了什么章"，还要定死**"必须/应/可"各自的效力**。混用的后果是读者不知道哪句要遵守——而这在一份会被下游当契约引用的文档里是致命的。

| 动词 | 效力 | 违反的后果 |
|---|---|---|
| **必须 / 不得 / 禁止** | 规范 | 实现不符即缺陷，须走变更评审 |
| **应 / 不应** | 规范，允许有理由偏离 | 偏离须在 3.c 登记理由与失效条件 |
| **可 / 可以** | 非规范 | 无后果，不构成契约 |
| **说明 / 示例 / 推断** | 非规范 | 无约束力，不得被引用为要求 |

两条落笔纪律：

- **一条契约只用一个动词，不叠用。** "应必须""建议必须"这类叠加句，读者只能自己挑一个信——那等于没写。
- **非规范内容必须显式标注。** 标题加"（说明）"/"（示例）"，表格上方加"以下为推断，非要求"。不标的话读者默认整篇都是规范——**而反向文档里绝大多数句子是描述、不是要求**，这是最容易造成误解的地方。

> **反向档整篇默认非规范，它是记录。** 只有 3.e 判为 `一致` 的事实、以及签发后经客户确认的条款，才具备规范效力。这一点要在文首说清，不能指望读者从"状态：As-Built"自己推——多数读者根本不知道 As-Built 意味着什么。

#### 1.6 阅读路径与代码地图

接手的人有三个层次的需求，满足上一档不等于满足下一档：

| 档 | 需求 | 文档要给什么 |
|---|---|---|
| 读懂 | 知道它做什么 | 功能表、框图、术语表 |
| **敢改** | 知道改哪里会牵连谁 | 接口契约、时序契约的**影响面**、职责边界 |
| 能查 | 出事时知道去哪看 | 状态寄存器、错误上报路径、内部状态可观测出口（第 3 章末）、波形附录 |

**"敢改"这一档最缺。** 接口表只写"谁连谁"，不写"谁被谁阻塞"；改一个信号前，新人推不出影响面。所以除了 `peer` 列，时序契约表要给出**影响面**：这条契约失效时谁会被拖下水。

**阅读路径**一句话写清：先读哪章、哪几节是必读、哪几节可以跳过（比对不同角色给不同路径：集成 / 驱动 / 验证 / 接手维护）。

**代码地图**是文档与 RTL 的对应关系，交接时是刚需：

| 模块 | 主要文件 | 建议先读哪个 | 备注 |
|---|---|---|---|
| 顶层 | `top.sv` | 例化与连线 | — |
| 模块 A | `moda_ctrl.sv` / `moda_dp.sv` | `moda_ctrl.sv` 状态机 | 数据通路由控制态驱动 |

边界的判断要写进来：**1000 行不是问题，需要读者自己重建多少独立决策才是。** 1000 行、三个 module、契约清楚 → 读得动；300 行、边界模糊、状态藏在 always 块顺序里 → 读不动。压缩的是"需重建的决策数"，不是代码行数。

### 第 2 章 功能描述

- 2.1 应用场景与使用方式（谁调它、解决什么问题）
- 2.2 功能列表（固定列见下，每条可被验证追溯）
- 2.3 功能框图（数据从哪里来、到哪里去）
- 2.4 工作模式与配置组合（模式矩阵：哪些模式互斥、切换代价）

功能表固定列（**与模板 2.2 必须一致，改一处就两处一起改**）：

| id | 功能 | 支持状态 | 分级 | 验收判据 | 说明 / 出处 |
|---|---|---|---|---|---|
| F-01 | 单次事务的发起与完成 | 路径存在 | P0 | 拉起 `start` 后 3 拍内 `busy=1`，完成后 `done` 恰 1 拍 | `IDLE` 中按源端满空判定，见 5.2 |

**"验收判据"列不能空。** 它是"这条功能做对了"的客观标准，也是 `可裁决` 判据在第 2 章的落点——空着就等于这条功能没有判定依据，验证只能自己猜预期值。

支持状态只有三个取值，不许自造：

| 取值 | 判定标准 |
|---|---|
| 路径存在 | 存在实际赋值、状态更新或例化连接 |
| 条件存在 | 需参数、宏或运行时输入取特定值；"说明"列必须写清条件 |
| 无路径 | 已固定关闭或端口未接入；不表示代码里没有对应模块 |

**这一列只回答"代码里有没有这条路径"**，不回答"设计对不对、验没验过"——设计意图未确认的标 `[?Q-xx]`，验证证据看 6B.1。写"已实现"会被读成"已确认正确并通过验证"，这与 6B.1"无仿真证据"并列时就是自相矛盾。

**仅有参数声明或 generate 框架、没有实际数据通路的能力，不得标"路径存在"。** 这是反向 spec 最容易夸大的一处。正向文档里对应的是"计划支持 / 条件支持 / 裁剪"，裁剪必须回到**第 1 章 1.3** 记原因。

分级按实现依赖排，不按重要性排——它同时是验证优先级：

| 级别 | 含义 | 判定 |
|---|---|---|
| P0 | 基础运行路径 | 缺了它模块根本不能用：复位值、基本事务能否发起与完成 |
| P1 | 完整功能 | 各功能在正常配置下都能工作：各模式、各路径、各分支 |
| P2 | 边界与完善 | 极端值、并发、异常注入、性能相关 |

这个分级在第 6 章会直接变成 FP 的分级，进而决定验证先做哪一批。**P0 未覆盖完不该去磨 P2**——不写明这句，验证会按覆盖率数字平均用力，最后 P0 有洞而总体数字漂亮。

> 验收判据放这里或第 8 章，但必须有：功能"做对了"的客观标准是什么。反向文档里这条尤其要紧——客观标准若只来自 RTL，就退化成"代码即标准"。

### 第 3 章 架构设计

四类图缺一不可：

| 图 | 画什么 | 评审看什么 |
|---|---|---|
| 结构图 | 模块层次与数据流 | 模块职责是否单一、有无环形依赖 |
| 分块图 | 单模块内部划分（控制/数据/存储） | 关键路径落在哪一级 |
| 计算映射图 | 算法算子 → 硬件资源映射 | 复用是否成立、并行度依据 |
| 时序图 | 关键交互的拍级顺序 | 握手是否闭环、有无死锁可能 |

**每张承载值的图都配一张表**（见总则 0.2.1）。判据不是"有图就必须有表"，而是**这张图里有没有能被指出错的确切取值**：

| 图 | 配什么 | 为什么 |
|---|---|---|
| 结构图 / 数据流图 | 职责边界表（职责 / **不做什么** / 责任人） | 图给拓扑，表给图表达不了的维度——**不是复述方框** |
| 分块图 | 资源账 | 图给划分，表给深度 × 位宽 × bank |
| 计算映射图 | 算子表 | 图给数据怎么走，表给并行度与复用次数 |
| 时序图 / 波形图 | 「拍号 / 信号 / 期望值 / 前提」四列表 | 图给形状，表给判定依据——**这一项不能省** |

纯拓扑图、模块框图本身已是完整信息，不必再造镜像表：图上有五个方框就造五行表复述，等于两份数据手工同步，必然漂移（同附录 A 的纪律）。图负责让人看懂，表负责让人判定，两者的分工是**粒度不同**，不是一一对应。

每个模块六要素：

1. **职责**：一句话，边界清晰（不做什么也要写）
2. **端口表**：见下方固定列
3. **时序契约**：几个 cycle 出结果、什么条件打拍、反压如何传播
4. **状态机**：状态列表 + 转移条件 + 复位值 + 闭环检查（任意状态可达 IDLE，无死路）+ **跳转原理**
5. **实现方式**：数据通路四要素 + 算子表 + 资源账 + 精度口径（见 3.a）
6. **异常与复位**：错误注入后如何恢复、复位是否分级（硬复位 / 软复位 / 域复位）

> 下列 3.a–3.d 是四个跨模块通用的写法要求，标号带字母以免与各模块的 3.x 小节冲突。

#### 3.a 「实现方式」要写什么：决策，不是语句

这一节最常被写成一行"采用三级流水"，等于什么都没说。它要回答的是**电路怎么算、数据怎么流、状态放哪里**——三个动词加一个控制，缺一个验证就给不出预期值。

**（1）数据通路四要素**

| 要素 | 要写死的内容 |
|---|---|
| 传输 | 数据从哪进、经过哪几级、每级做什么；**生命周期**——进 buffer 后谁负责释放、credit 怎么回收、指针回绕怎么处理 |
| 计算 | 每级做哪类运算、并行度、复用几次；组合链深度预判 |
| 保存 | 存什么、放哪（SRAM / 寄存器堆 / FIFO）、深度 × 位宽 × bank 数、单口还是双口 |
| 控制 | 谁来驱动上面三者的时序（状态机 + 计数器 + 握手） |

**"传输"只写路径不算写完。** buffer 泄漏和 credit 虚占是集成期最难查的一类问题：功能看着都对，只是带宽慢慢掉下去，因为没人写"用完谁释放"。

**（2）算子表：算法到硬件的映射**

| 算子 | 硬件资源 | 复用次数 | 并行度 | 每拍产出 | 依据 |
|---|---|---|---|---|---|
| 8-bit MAC | MAC 阵列 16×16 | 1 | 16 | 16 MAC/cycle | 算力预算见 2.2 |

这张表是主管判断"方案合不合理"的第一落点：复用次数决定吞吐，并行度决定面积，两者的乘积必须能倒推回架构阶段的算力预算。

**（3）资源账**

| 资源 | 类型 | 深度 | 位宽 | bank | 端口 | 用途 | 冲突仲裁 |
|---|---|---|---|---|---|---|---|
| `line_buf` | SRAM | 512 | 128 | 2 | 单口 | 行缓存 | 读写互斥，写优先 |

只写"存在 SRAM 里"没有用。这张账直接决定面积和功耗，也是评审最该算出问题的地方：深度改了面积要重算，端口数改了冲突策略要重写。有 ECC 的写清纠检能力与代价。

**（4）精度口径：最容易漏、后果最重**

| 项 | 必须写 |
|---|---|
| 累加位宽 | 中间结果几位，为什么够（不能写"足够大"） |
| 截位 / 饱和 | 溢出是回绕还是饱和到边界值 |
| 舍入方式 | 截断 / 四舍五入 / round-to-even |
| 定点位置 | 小数点位在哪，是否有动态缩放 |

这一项缺失是 AI / DSP 类模块验证给不出预期值的头号原因：算法侧说"INT8 累加"，硬件用 32 位还是 24 位、溢出饱和还是回绕，文档不写，验证只能猜，而猜错的方向通常是"两边都自认为对"。

**（5）不写什么**

语句与风格不写（`if (cnt == 4'd7)`、三段式还是两段式、信号命名前缀）。理由见总则 0.5：那属于实现自由度，写进契约会锁死方案，还会在偏离后造成"文档与代码信哪个"的混乱。

#### 3.b 状态机：表有三张，散文只有一个用途

状态机这一节真正要交的是**三张表 + 3–5 句散文**。三张表各回答一个不同的问题，缺哪张都会让读者拿另一张去凑答案，而凑出来的答案经常是错的：

| 表 | 回答什么 | 只有它能回答的 |
|---|---|---|
| **状态转移表**（带判定顺序） | 从哪到哪、什么条件下 | 多条件同拍时的唯一结果 |
| **状态 × 输出矩阵** | 处在某态时外部看到什么 | 驻留期间的电平，而不是"某条边置了某位" |
| **不变量表**（INV-xxx） | 无论怎么跑都必须成立什么 | 无激励即可判的恒真约束 |

**为什么会写成三张而不是一张**：只用转移表，读者只能从"某条转移发生时置了某位"倒推驻留输出——这个倒推恰好是时序错误的第一来源（反向文档里 P0 级错误几乎全出在这条路上）。只用输出矩阵，读者不知道怎么就跳了。只看两张表，读者仍然不知道"某态连驻留两拍算不算违规"——那是不变量的活。

##### 转移表：判定顺序是硬事实，不是解释

代码里状态寄存器是一条 `else-if`（或 `case` + `if`）链，**顺序就是优先级**。同一拍多个条件同时成立时，谁赢由这个序号决定，与"哪个更合理"无关。把它写成散文"优先处理 A"，读者推不出多条件同拍的唯一结果。

两处必须显式落表：

- **判定顺序列**（1 / 2 / 3 …），不是塞进"条件"格里加个"优先"字样
- **兜底的"保持本态"单独列成最后一行**，不许省。省掉之后读者不知道"条件都不成立"时会发生什么——而这正是"没响应 / 卡死"类缺陷的藏身处

另加一列 **驻留性质**（单拍 / 多拍 / 自环）：标"单拍"的状态不允许连出两拍（直接对应一条 INV），标"自环"的才是真正会等的那个，性能瓶颈只可能在这里。这一列看着多余，其实决定了后面所有时序纪律能否被检查。

##### 输出矩阵：Moore 与 Mealy 不许混排

行是状态，列是各使能 / 控制输出。**按"状态"组织，不按"转移"组织**——这是它与转移表的根本分工。

- **Moore 输出**（只看状态）：格内写电平，或标"单拍脉冲"
- **Mealy 输出**（同时看输入）：单列一栏，或格内明确标 `(Mealy: 依赖 XX)`

混排的后果是具体的：验证侧按 Moore 去写断言，只检查状态就以为覆盖了，输入路径那一半漏掉了。**时序属性不同的东西放在同一格里，等于声称它们一样。**

##### 不变量表：INV 与 VP 是两类东西，不能合并

**不变量是恒真声明，不需要激励就能检查；VP 需要给激励、看预期。** 混在一起的典型症状是把"给一次完整传输，done 宽度恰 1 拍"写进 INV——那不是恒真，是场景。

| 适合进 INV | 适合进 VP |
|---|---|
| 某状态不得连续驻留超过 1 拍 | 给一次完整传输，观察 done 宽度恰 1 拍 |
| 某两态互斥，不可能同拍有效 | 并发发起两个请求，观察仲裁结果 |
| 复位期间某输出不得为高 | 复位释放后第一拍观察各输出初值 |
| 计数不越界、指针在条件下不回绕 | 灌满缓冲，观察满标志出现时机 |
| 某输出与某状态严格同沿（或严格晚 N 拍） | 跨边界传输，观察该输出相对状态的拍位 |

**每条不变量都要写"为什么必须成立"**。写不出理由的，多半只是描述了一个实现细节——这种"不变量"会随改版立刻失效，反而成为评审噪音。

> INV 只到**语义级**：写"done 宽度恰为 1 拍"可以，写 `##1 !done` 这种具体 SVA 语法不行。断言库、绑定方式、覆盖率 bin 归验证侧，边界见 `fp-vp-generation.md` 开头那段。

##### 散文只剩一个用途：讲划分理由

跳转表、输出矩阵、不变量都是硬事实，照着 RTL 谁都能填。真正只有人能写的是**为什么这么划分**：

| 要回答 | 为什么重要 |
|---|---|
| 为什么拆成这几个状态 | 状态划分错了，整个实现方案跟着偏斜，而三张表本身都看不出问题 |
| 为什么不合并 | 合并会省面积但引入什么风险（时序耦合、复位复杂、可观测性下降） |
| 为什么要有这个中间态 | 例如 `LOAD` 态存在是因为 SRAM 读有 1 拍延迟，不是为了好看 |
| 哪个状态是性能瓶颈 | 自环等待的那个态，决定了最坏延迟 |

**主管评审状态机看的不是"条件写全了吗"，而是"划分合理吗"。** 前者能机器查，后者只能靠人判，而后者才是文档存在的理由。所以正文**必须有 3–5 句散文**讲清划分依据——这是全篇唯一放宽到 5 句的地方（见总则 0.2 的例外表），理由是这四个问题各需一句，压到 3 句必失真。

再加上**每个控制信号的复位后初值**（不是"复位后清零"，而是逐信号给出，尤其是有多个复位域的）——这条属硬事实，常被漏。

**三项纪律，反向文档尤其要守（反向 spec 被逐条审查时，P0 级错误几乎全部出自这三处）：**

**① 外部可见行为按"采样沿之后"写，不按转移过程写。** 状态寄存器与输出寄存器常在同一时钟沿更新，外部看到的是"更新之后"的值。写成"`done` 在 STOP 态置高、下一拍进 IDLE"，读者会理解成 `done` 与 STOP 同拍——实际可见的是 `IDLE + done` 同拍。**判据**：对每句"X 在 Y 态可见"，问"这两个信号是否同一时钟沿赋值"；是，就按同沿之后写。正确写法：`done 的前置握手被采样后，下一拍状态变 IDLE 且 done 为高，再下一拍 done 清零`。

**② 派生指示信号给递推式，不给"延迟 N 拍"。** `activity[n] = (state[n-1] != IDLE)` 一个公式同时覆盖了：高电平窗口、启动边界晚一拍、停止边界多保持一拍、以及它对使能撤销判断的影响。"有 1 拍延迟"这种散文，换四个章节各写一遍仍是四处漏定义，还容易改一处漏三处。三类输出要分开交代：**与状态同沿更新**（外部同时可见）/ **派生指示**（晚一拍，给公式）/ **组合译码**（同拍变化但占空比不同）。

**③ 功能前提必须穷尽到状态寄存器的门控分支。** 状态寄存器 `else-if` 链上的每条强制归位 / 保持条件，都是所有相关功能的前提。写"缓冲非空且总线空闲就发起"，漏掉"使能撤销时空闲强制归位"，验证就会搭出一个永远进不了启动态的激励，然后争论是 RTL 错还是文档错。做法：把状态寄存器赋值条件按分支拆开，逐条问"这条不成立时哪些功能不能发生"；**端口表里已经记过的门控，必须同句进功能前提**——一处 known、另一处漏掉，是最典型的交叉失配。

#### 3.c 关键决策台账

第 3 章只写结构不够，还要写**为什么是这个结构**。交接时最需要的"为什么"和"什么条件下会失效"，目前只有这里能放。按 `arch-budget.md` 第 4 节的三段式，一张表收完：

| 编号 | 决策 | 备选方案 | 选它的理由 | **失效条件** |
|---|---|---|---|---|
| D-01 | 卷积阵列 16×16 空间阵列 | 8×8 + 双倍频率 | 1 GHz 下算力达标，关键路径 MAC 树 4 级 | 工艺降到 800 MHz 上限则算力不足，需改回双阵列 |

**失效条件一列不许空。** 没有失效条件的决策，等于承诺永远正确——这种决策三个月后没人敢动，六个月后没人记得为什么。

#### 3.d 内部状态的可观测出口

验证从端口看进去，看不到状态机停在哪、buffer 里几个数据、指针指向哪。**"出问题时只能比对文档"，可比对的前提是他能看到某个东西。** 所以第 3 章末尾要有一张映射表：

| 内部状态 | 出口 | 读法 / 时序 |
|---|---|---|
| `state` 当前值 | `STS.STATE[3:0]` | 直接读 |
| buffer 占用数 | `STS.OCC[7:0]` | 读，注意采样有 1 拍延迟 |
| 当前描述符指针 | **不暴露** | 只能由 `cur_desc` 端口间接推断 |

**第三行才是这张表真正的价值：明确写出"看不见"。** 验证看到它就不会白费力气找观察点，也不会写出一条"直接驱动内部信号"的 VP（那类 VP 在 `fp-vp-generation.md` 里是禁止的，但禁了以后必须给出替代路径，这张表就是替代路径）。

这张表同时回答主管的第四个问题"出了问题查得出来吗"——芯片回来后调不出来，通常不是因为逻辑错，是因为当初没留出口。

### 第 4 章 寄存器与配置

**一个 IP 只有一张寄存器主表。** 明细与汇总两个视图都要有，且必须同源一致。

#### 4.1 地址段分配（多模块 IP 必写，单模块 IP 也写）

| 段名 | 起始 | 结束 | 大小 | 归属模块 | 余量用途 |
|---|---|---|---|---|---|
| CTRL | 0x0000 | 0x00FF | 256 B | 全局控制 | 预留 64 B 给后续中断扩展 |
| MODA | 0x1000 | 0x1FFF | 4 KB | 模块 A | 无余量，已用满 |

段规则：
- 段区间**不重叠、不跨界**，起止按声明的对齐粒度（通常 4KB）
- 每段容量能容纳该段全部寄存器且有余量，余量要写清用途（预留 / 后续扩展）
- 外部 IP 的段标「外部交付，见 XX 手册 Vx.y」，**不展开明细**——这是唯一合理的表外之表

#### 4.2 明细表（主表）

固定列：

| offset | name | bits | field | msb | lsb | attr | reset | description |
|---|---|---|---|---|---|---|---|---|
| 0x000 | CTRL | 32 | EN | 0 | 0 | RW | 0x0 | 模块使能 |

规则：
- **offset 一律写绝对地址，不写相对地址。** 每个子模块都从 0x000 起写，看着整齐，实际上驱动工程师要自己拼地址、拼错就读到别人的寄存器；两份表都出现 0x000 且名字不同，机器无法判冲突；改一段段大小，所有下游表手工重算
- 同一 offset 在明细与汇总中命名必须完全一致（拼错一个字母就是缺陷）
- 章节标题声明的 offset 必须与表内一致
- 位域不得重叠，msb ≥ lsb，msb < 寄存器位宽
- 非 Reserved 位域必须有 attr 与 reset
- 位域 reset 合成后必须等于寄存器 reset
- offset 4 字节对齐，重复 offset 是错误
- 每个寄存器配一张位域图（评审时最容易被要求补的东西）
- 同一寄存器在多个模块有镜像视图时，**两个 offset 各占一行**，在 description 里交叉引用，不要合并成一行

**反向文档在末列加 `evidence`**，填源码位引用（如 `ctrl_reg[0]`），并标 `measured` / `inferred` / `TBC`。attr 与 reset 两列在反向文档里最容易凭经验填：凡源码里读不出写清路径的位（例如只被条件分支写入、或写使能来自外部），evidence 列要写清读法而不是填个值了事。**复位值读不到时不许留空**——给出最可能的候选值并标 `inferred`，两者相差会导致下游复位行为不同的，追加 `[?Q-xx]`。

#### 4.3 分模块明细（主表的切片）

多模块 IP 在第 4 章按模块分小节，例如 4.3 模块 A、4.4 模块 B。

**这不是第二张表，是主表按模块的切片**：每行仍写绝对地址，列一个不少。切片只改变阅读顺序，不改变事实。

#### 4.4 冲突检查（交给脚本，不靠人眼）

| 检查项 | 判定 |
|---|---|
| 段外地址 | 明细行 offset 落在 4.1 声明的任何段之外 → 错误 |
| 段重叠 | 两个段区间相交 → 错误 |
| 地址重叠 | 两行 offset 相同 → 错误 |
| 命名漂移 | 同一 offset 在不同小节名字不一致 → 错误 |
| 位域重叠 | 同一寄存器内 field 的 [msb:lsb] 相交 → 错误 |
| 复位不一致 | 位域 reset 合成后 ≠ 寄存器 reset → 错误 |
| 位宽越界 | msb ≥ 寄存器位宽 → 错误 |
| 属性缺失 | RW/RO/WO 之外的值，或非 Reserved 位域缺 attr/reset → 错误 |

这些都能机器判，不要写进人工评审清单占篇幅。

### 第 5 章 接口定义

接口表固定列：

| signal | direction | width | clock domain | protocol | peer | description |
|---|---|---|---|---|---|---|
| s_axil_awaddr | in | 10 | aclk | AXI4-Lite | CPU | 写地址 |

规则：
- 位宽写数值或明确参数名及默认值，**不要写 `N` 或 `N/8`**
- 每个信号标时钟域；异步接口单独列同步方案
- 协议接口按通道分组（AW/W/B/AR/R），标 outstanding 深度
- 复位信号写清极性、同步/异步、复位域

**反向文档在末列加 `evidence`**，填端口声明位置（文件:行号）。**端口存在但不被消费的必须单独标注**：只在敏感列表出现、或声明后从未引用——这类信号仍列进表，但 description 写明未参与功能，并进附录 E。这是集成阶段返工的主要来源。

**跨模块接口还要加一列「时序前提」**：这个信号相对谁、晚几拍、是不是单拍脉冲、组合还是寄存。反向文档里这一列尤其不能省——本模块只能证明"我怎么用它"，证明不了"它什么时候来"。**这一列填的是"相对哪个信号、在什么边界上有效"**，四类典型写法：

```
<握手完成类>  ：与对端 <某响应> 同拍有效，本模块在下一拍采样
<数据有效类>  ：与 <数据总线> 有效同拍，不可组合穿过本模块
<脉冲类>      ：单拍脉冲，不得连续两拍为高
<门控类>      ：与 <本域时钟> 同步，可作为组合门控使用
<读返回类>    ：读使能后 N 拍数据稳定，N 由对端规格给出
```

> **不许留空、也不许写"见对端文档"**。留空意味着你在假设"它跟时钟一样随时可用"，这是跨模块集成最常见的返工来源；写"见文档"等于把判断推给读者，而读者看的正是你这份。判断不了就按第 5.1.3 编号成 `A-xx` 假设，写明"若不成立影响哪些条款"。

**为什么必须逐条写、不能只集中在一处问一次**：每个功能都有自己的验收前提。前提只在问题清单里提一句，验证环境就会按各自的理解搭接口模型——两边假设不一致时，仿真照样"通过"，因为两边错得一致。

#### 5.1.1 参数化位宽怎么处理

规则"不写 N"的目的是**可核对**，不是禁止参数化。凡位宽由参数推导的信号（AXI 的 `awlen` 随 outstanding 深度变、`wstrb` 随数据宽度变），按三段式写：

| signal | direction | width | clock domain | protocol | peer | description |
|---|---|---|---|---|---|---|
| m_axi_awlen | out | **AWLEN_W** | aclk | AXI4 | DDR 控制器 | 突发长度，AWLEN_W = clog2(MAX_BURST) |

三条要求，缺一条就算不合格：

1. **位宽写参数名，不写表达式**。写 `$clog2(BURST_LEN_MAX)` 无法核对；写 `AWLEN_W`，然后在下方面板定义它
2. **文档内必须给出闭式定义 + 取值表**，让读者能算出实际值：

   | 参数 | 定义 | 典型取值 | 位宽 |
   |---|---|---|---|
   | `MAX_BURST` | 单次突发最大拍数 | 256 | — |
   | `AWLEN_W` | `clog2(MAX_BURST)` | 8 | 8 bit |
   | `DATA_W` | 数据通路位宽 | 128 | — |
   | `WSTRB_W` | `DATA_W / 8` | 16 | 16 bit |

3. **至少给出一个配置点的实际位宽**，让验证能直接建模型。只给参数不给取值 = 变相的 `N`

**禁止写法：** `width` 列填 `N`、`N/8`、`见参数`、`—`。这四种都不可核对。

#### 5.1.2 协议接口的通道表

AXI / AHB / APB 这类协议接口，除信号级表外必须给一张通道概览，否则集成时算不清带宽：

| 通道 | 方向 | 位宽 | outstanding 深度 | 备注 |
|---|---|---|---|---|
| AW | M→S | AWID_W / AWADDR_W | 4 | 写地址 |
| W | M→S | DATA_W / WSTRB_W | — | 写数据，不独立 outstanding |
| B | S→M | BID_W | 同 AW | 写响应 |
| AR | M→S | ARID_W / ARADDR_W | 8 | 读地址 |
| R | S→M | RID_W / RDATA_W | 同 AR | 读数据 + 响应 |

outstanding 深度不是随手写的数字，它由带宽需求 ÷ 单次传输字节数算出，**要把算式写在同一节**。这一列是后续性能不达标的头号原因。

#### 5.1.3 外部协议假设（A-xx）

**本模块的行为有一半由外部决定时，那些决定就是文档的前提，必须独立编号。** 否则同一句假设散落在功能表、状态机、VP 三处，措辞各异，改一处漏两处。

| 编号 | 假设 | 若不成立，影响哪些条款 | 谁能确认 |
|---|---|---|---|
| A-01 | 对端握手响应与数据有效同拍，本模块在下一拍采样 | F-05、F-09、VP-09.x | 对端模块规格 / 设计者 |
| A-02 | 各完成信号为单拍脉冲，不会连续两拍为高 | 全部等待态 | 同上 |
| A-03 | 存储读接口为同步读，使能后 2 拍数据有效 | 3.3.4、F-11 | 存储封装方 |

> **示例里的"对端握手响应""完成信号""存储读接口"是角色名，不是真实信号名。** 落到具体文档时要换成自己模块的端口名——但**写进假设表的永远是角色 + 时序关系，不是某次评审里出现过的名字**。这条看着琐碎，实际是防止把上一份文档的图示和假设原样搬进下一份。

三条规矩：

- **功能、状态机、VP 只引用编号，不重述假设**——重述就会分叉
- **每条假设都要写"若不成立影响谁"**，否则读者无法判断它值不值得追问
- **假设不是问题**：问题清单是"我不知道、需要有人答"，假设是"我按这个往下写了、请确认"。两者分开编号（Q / A），答复后 A 改成"已确认 vX.Y"，Q 改"已确认"并保留

### 第 6 章 验证方案

**这一章叫"验证方案"，写的却是设计侧交给验证侧的输入**：验证要做什么、边界在哪、哪些行为最可疑。验证怎么做——TB 结构、sequence、testcase、断言、coverage bin、覆盖率目标与实测、回归流程——属于验证侧的《验证计划》，不写在这里。

判断标准只有一条：**本章的每一句，是否能由设计者独立写出并负责。** 写"采用 UVM 环境"越界了（那是验证方选型）；写"本模块不验跨时钟域数据一致性，由系统级覆盖"没越界（那是设计侧的边界声明）。

两种形态，取决于 spec 是正向还是反向。**交付对象相同**：验证工程师照着它列用例。

#### 6A 正向形态：验证交接

RTL 尚未存在，本章内容全部从契约（第 2/3/5 章）推导。

- **6A.1 验证范围与不验范围**——设计侧声明边界。不验的部分**必须写理由**（例如"跨模块路由由整 IP 集成验证覆盖"）。这一条是设计侧的责任：只有设计者知道哪些行为在自己的模块里闭合、哪些依赖上层。
- **6A.2 重点风险与必测行为**——设计者最清楚哪里容易错：跨时钟域、异常路径、参数边界组合、协议边缘。列表形式，每条说清"为什么这里是风险"。**这不是用例清单**，是给验证方的注意力分配建议。
- **6A.3 功能点与验收观察点清单**——按 `references/fp-vp-generation.md` 生成 FP/VP。**本章的核心产出**，篇幅与工作量最大的一节（6A 五节都是必填，但这一节是唯一"内容要做全"的：其余四节各三五句或一张表即可收口）。
- **6A.4 验证基线声明**——四句话，与 6B.3 同格式：覆盖了哪些条款、哪些没覆盖及原因、P0/P1/P2 各多少条且哪些 P0 尚无 VP、哪些条款给不出可判定的预期结果。
- **6A.5 本章不包含什么**——把边界写出来，避免使用方以为缺口已有人负责：TB 与验证组件、sequence/testcase、断言与 coverage bin、覆盖率目标与实测数据、回归与持续集成流程。**这些全部归验证侧。**

#### 6B 反向形态：验证基线

第 6 章不写"打算怎么验"，写"当前实现已验证成什么样 + 交给验证的基线是什么"。四块：

**6B.1 已验证 / 未验证 / 存疑三态清单**

| 取值 | 含义 |
|---|---|
| 已验证 | 有形式化或仿真证据，能指到具体用例 |
| 未验证 | 无证据，且未安排 |
| 存疑 | 有证据但被降级、或结果未能复现 |

降级通过不等于通过。有残留诊断的，把条数写出来，别写"基本通过"。

> 这一节是 6B 独有的：反向场景下 RTL 已跑过一轮，设计侧有义务交代**现状**。正向场景没有这一节——那时还没有可交代的验证状态。

**6B.2 功能点与验收观察点清单**

按 `references/fp-vp-generation.md` 生成，交付给验证工程师作为验证计划的输入。FP 必须带 **P0/P1/P2 分级**（来自 2.2）与**证据等级**两列——前者定验证优先级，后者告诉验证方哪些预期值最可疑。

| FP | 名称 | 分级 | 证据 | 依据条款 | 覆盖的 VP |
|---|---|---|---|---|---|
| FP-03 | 事务启动判定 | P0 | measured | 2.2 / 5.2 | VP-03.1～03.4 |

**6B.3 验证基线声明（必写）**

四句话讲清，缺一句验证方就会误用：

1. 本清单覆盖了哪些条款，哪些没覆盖、为什么
2. P0/P1/P2 各多少条，哪些 P0 还没有对应 VP
3. 哪些 FP 的证据是 `inferred` 或 `TBC`——这些预期结果最可能错
4. 附录 E 每条限制导致哪些行为无法给预期结果

**6B.4 适用范围与能力边界**

必须写明两层边界：

**一层是验收口径**：本 VP 清单可作为**回归基线**与**改动影响分析**的依据；**需求正确性**的判定不来自本文档。理由要写出来，别只写结论——反向 spec 的预期结果取自 RTL 实现，单靠它验证等于用实现验证实现，实现里的缺陷会被写成"预期行为"而永久通过。这条不写，验证方会把 VP 当保证值用。

**二层是职责边界**：本文档产出到 VP 为止，是**验证的输入**而非验证本身。TB/sequence/testcase、断言与 coverage bin、跑仿真、覆盖率缺口分析，属验证环境，不在本文档范围。写清这条，避免使用方以为缺口已有人负责。

**6B.5 与 6A 的差别（一句话）**

| | 6A 正向 | 6B 反向 |
|---|---|---|
| 时态 | 将来："要验这些" | 现在："已验成什么样" |
| 6B.1 三态清单 | **没有**（还没验过，无可交代） | **必写** |
| 证据等级列 | 不需（条款来自意图） | **必填**每 FP |
| 能力边界 | 不需声明（契约本身有权威） | **必声明**（预期取自 RTL，有自证风险） |

**两边的产出物形状一样：一份带分级的 FP/VP 清单 + 一份基线声明。** 差别只在证据来源和要不要交代现状。

### 第 7 章 闭环完整性（不许裁）

**前面六章各写各的，只有这一章能回答"有没有漏掉什么"。** 它把「需求 → 规格 → 实现 → 验证」四段接成一条链，是三样东西的合集：

| 内容 | 回答的问题 | 缺了会怎样 |
|---|---|---|
| 需求追溯矩阵 | 每条需求落在哪、由谁验 | 需求在传递中静默掉队，没人发现 |
| V 模型闭环检查表 | 每个环节的**验收方法**有没有先于实现定下来 | 做完再想怎么验，通常验不全 |
| 未闭环清单 | 已知缺口是什么、谁负责 | 空着等于宣称全闭环，评审必抓 |

**7.1 需求追溯矩阵**。一条需求一行，五列：需求编号 / 描述（一句）/ 落到规格哪节 / 落到实现哪个模块 / 由哪些 VP 覆盖。写"见第 3 章"无效——那等于没落。

判据两条，都是双向的：

- **每条需求至少一个 VP**。没有 VP 的需求，要么不该进范围（写明为什么不做），要么是缺口
- **每个 VP 能倒查到需求**。倒查不到的 VP 说明在验一个没人要求的行为——要么需求漏了，要么用例多余

这两条一起用才是闭环。只查前一条，会漏掉"多验了一堆没人要的东西"；只查后一条，会漏掉"需求忘了落"。

**7.2 V 模型闭环检查表**。逐环节问的不是"做了没有"，是"**这个环节的验收方法定了没有**"。方案已确认但方案验收方法未定，结论一律记断点——不许写"后续补充"，那只是把缺口换了个说法。判据很简单：**先定验收再做设计，是 V 模型；做完再想怎么验，是倒推。**

**7.3 未闭环清单**。查出的缺口逐条登记：缺口 / 类型（需求无 VP、VP 无需求、环节未确认、明确不做）/ 影响 / 谁负责 / 计划。

**"明确不做"也必须登记理由。** 决定不做和忘了做，在文档里必须能区分开——否则半年后没人知道某条需求是"商量过不要"还是"漏了"。

**反向（as-built）档的处理：这一章保留，且不许留空白。** 旧做法写"多为 TBD 行"是错的——客户把 RTL 交过来，目的是让你替他抽象出一份能评审的文档，**留空等于把工作原样退回**。正确做法是造候选：

**① 先出 `REQ-xxx` 候选，哪怕全部 `TBC`。**

| 需求编号 | 反推出的行为描述 | 证据（实现位置） | 状态 | 关联问题 |
|---|---|---|---|---|
| REQ-001 | | 文件:行 / 状态机名 | `TBC` / `inferred` / `已确认` | Q-xx |

- **不复用客户 PRD 编号**——复用会让人误以为这条需求出自 PRD
- **只写"实现表现出的行为"**，不写"设计者意图"；意图不明的追加 `[?Q-xx]`
- **一条都造不出来是异常信号**，不是"本模块无需求"——通常说明功能表切错了（按模块/always/字段切的，不是按行为切的）

**② 文首必须有防冒用声明**（放在证据状态声明之后）：

> 本章需求条目由 RTL 实现反推得出，**不是客户原始需求**。与客户 PRD 冲突时以 PRD 为准；本表仅用于建立"实现 ↔ 验收"的可追溯关系，不得作为需求基线引用。

这段不是免责话术。反推需求最危险的用法是被下游当成原始需求去实现下一个模块——**声明要出现在这个误用发生之前**。

**③ 追溯矩阵照常填，未确认项标 `TBC` 而不是删行。** 五列里只有"描述是否与客户本意一致"填不出来，那一列标 `TBC` 并指 `Q-xx`；编号、落点、VP 覆盖三列都填得出来。

**④ 全部行都是 `TBC` 时，标题必须改。**

> `## 7.1 需求追溯矩阵（评审议程 —— 尚未建立追溯）`

加一句：「本表当前全部条目待确认，**不构成追溯矩阵，而是待客户确认的评审议程**。追溯关系在至少一条 `REQ` 被确认后建立。」

**为什么改标题而不是只标 `TBC`**：标题是读者判断"这段能不能引用"的第一依据。标题写"追溯矩阵"、内容全 `TBC`，下游会当成已建立追溯——这与"清单说待确认、正文说确定"是同一种病，换了位置而已。**声明必须出现在读者犯错之前。**

**⑤ 闭环检查表八行全断点，如实写。** RTL 已经写完，前四环（应用场景、需求拆解、整体验收、方案确认）**在时间上就不可能先于实现**。逐行写断点是为了让客户看清断在哪、要不要补——**不是让你把断点写成"通过"去凑一张漂亮的表**。全断点且如实标注的反向文档，比半真半假的闭环表有用得多。

### 第 8 章 可测性与可制造性设计

这一章最容易写成"什么都在说、什么都不可验"。**每一节都要给判据：谁看、够不够的标准是什么。**

#### 7.1 DFT 约束

只写**设计侧必须提供的信息**，不写 DFT 团队自己会做的事（scan chain 怎么串、压缩结构选哪种，那是他们的活）。

| 必须写 | 合格判据 |
|---|---|
| 测试模式下的时钟行为 | 列出测试时哪些时钟被复用、频率上限、是否允许内部生成时钟。写成表，不写句子 |
| 测试模式下的复位行为 | 哪些复位在测试模式下固定无效/有效，有没有需要屏蔽的复位 |
| scan 使能/测试模式端口 | 端口名、极性、生效时机；测试模式下对功能逻辑的影响 |
| 需要 DFT 避让的逻辑 | 内部生成的时钟、门控单元、异步复位、模拟/存储实例，逐条列位置 |
| MBIST 接入 | 哪些存储可测、由谁加、测试模式下的访问冲突（谁优先） |

**不合格的典型**：写"本模块支持 scan 测试"——DFT 团队拿不到任何可执行信息。

#### 7.2 测试模式与功能模式的差异清单

一张表，两列对照：

| 项 | 功能模式 | 测试模式 | 对功能的影响 / 风险 |
|---|---|---|---|
| 时钟源 | PLL 输出 | 外部直供 | 频率上限降低，功能验证不覆盖此路径 |
| 复位 | 异步复位同步释放 | 固定释放 | 部分状态机可能停在非稳态 |
| 存储 | 正常读写 | MBIST 接管 | 测试期间功能无法访问 |

**这张表是流片前复盘的依据**：凡是"测试模式下与功能不同"的项，都是硅上调试时的迷路点。

#### 7.3 低功耗设计

按 power domain 写，每个域一行：

| power domain | 归属模块 | 可关断 | isolation 策略 | retention 需求 | level shifter 位置 |
|---|---|---|---|---|---|
| PD_TOP | 全局 | 否 | — | — | 与 PD_CORE 交界 |
| PD_CORE | 模块 A/B | 是 | 输出端 clamp 到 0 | 寄存器需保持 | — |

三条要求：**isolation 要写 clamp 到 0 还是 1**（写"需要 isolation"不可验）；**retention 要写哪些寄存器必须保持**；**level shifter 要写方向与位置**（谁驱动谁）。

#### 7.4 时序约束要点

不写完整 SDC（那是实现产物），只写**必须由设计者声明的例外**：

| 编号 | 类型 | 位置 | 理由 | 责任人 | 失效条件 |
|---|---|---|---|---|---|
| EX-001 | 多周期路径 | `u_dma/addr_calc/*` → `u_sram/addr` | 地址计算慢一拍，SRAM 有 setup 余量 | 张三 | 若 SRAM 换低延迟型号需重新评估 |
| EX-002 | 假路径 | `cfg_reg/*` → `datapath/*` | 配置寄存器静态，运行时不翻转 | 张三 | 若支持动态重配置则失效 |
| EX-003 | CDC 例外 | `aclk` → `mclk` 的 `data_vld` | 两级同步后使用 | 李四 | — |

**没有编号和失效条件的例外一律不接受。** 例外条目要编号（如 `[EX-001]`），否则三个月后没人敢删。**时序例外用 `EX-` 前缀，不要用 `FP-`**——`FP-` 已被功能点占用，两套编号撞在一起，评审时对不上号。

### 附录（常被要求补）

- A 寄存器完整列表（由主表汇总生成，按 offset 排序）
- B 接口信号完整表
- C 关键时序波形（每张波形先自检长度/取值再交付）
- D 描述符与数据格式位域（驱动和验证都靠它）
- E 限制与待确认项（反向文档必填，见下）

#### 附录 A / B 的生成纪律

**A、B 两个附录是生成物，不是手写物。** 手抄一遍主表，等于埋一处必然漂移的副本——某天门数改了、寄存器挪了，附录不会跟着变，而所有人都会以为附录是全的。

三种环境下怎么做，**按现实条件选一种并写在 1.3 行文规范里**（第 1 章）：

| 条件 | 做法 | 交付要求 |
|---|---|---|
| 已有寄存器生成流程（YAML/Excel → 文档） | 附录由脚本生成，文档里只放结果 | 表脚标注"由 xxx 生成，勿手改"+ 生成时间戳 |
| 没有流程但会用工具 | 主表维护在 CSV/YAML，交付用转换脚本出表 | 把源文件和脚本一起交付，写进 1.4 参考文档 |
| 全靠手写 | **不设附录 A**，改为「4.2 主表就是唯一寄存器表」 | 在第 1 章 1.3 登记"因无生成流程，不设附录 A，避免两份不同步" |

**关键是不允许出现"两份手工维护的同一张表"。** 第三种情况下，宁可少一个附录，也不能多一份副本——附录的价值是方便检索，主表的完整才是正确性。两者冲突时，正确性优先。

**索引就够了。** 想要"一页看全"的体验，在主表旁边加一张只含 offset / name / 所属段的紧凑索引（三列），由人维护出错概率低得多。

#### 附录 E 问题清单（反向文档必填）

这不是"未尽事项"，是**免责与交底**。评审时最先被翻的就是它，**空着的反向 spec 几乎一定是没查，而不是真没有**。

反向场景下它升级为**可回答的问题清单**（机制见 5.2.1）：每条带默认判断与级别，让审阅人回"确认/否认"即可。固定列：

| id | 问题 | 问题性质 | 本版默认判断 | 影响范围 | 谁能答 | 级别 |
|---|---|---|---|---|---|---|
| Q-01 | 某端口仅在敏感列表出现、未参与任何赋值：遗留端口还是预留？ | 接口清理 | 判为遗留端口，不写入功能表 | 5.1 端口表、附录 B | 设计 | **阻塞** |
| Q-02 | 缓冲深度 8 是算法要求还是面积妥协？ | 设计意图待确认 | 推定为面积妥协，进 3.c | 3.a 资源账 | 设计 | 重要 |

**问题性质四选一**：`疑似 RTL 缺陷` / `设计意图待确认` / `接口清理` / `外部规格缺失`。这一列不是为了分类好看——它决定后续动作：缺陷走修复、意图走确认、接口清理走裁剪、规格缺失走外部索取。不给性质的清单，审阅人得逐条自己判，答复率会掉一半。

**正文必须与清单联动，这是最容易自相矛盾的地方**：凡进了清单的项，正文一律降级为推断语气并标 `[?Q-xx]`。清单里写"意图待确认"、术语表里写"用于缓冲已空时仍发起一次传输"——读者只会信正文那一版，清单等于白写。**判据**：把清单每条与正文逐条对读，语气不一致就是缺陷。

**结论分三层写**（死端口、常量输出、异常路径缺失这类发现尤其要）：`RTL 事实`（代码里能证明的）/ `接口影响`（因此本模块对外不发出什么）/ `系统影响`（是否真出事取决于外部模块，本模块证明不了）。压成一句"总线不会产生 START"，就越过了证据边界——外部有没有别的启动机制，这份 RTL 里没有答案。

正向文档里这一节仍然叫"限制与待确认项"，用原来的四列（`id / 限制 / 影响范围 / 为什么文档内无法解决 / 责任方`）——有问题可以问人的时候，不需要"默认判断"这一列。

必须登记的四类（RTL 侧未明确）：

1. **未被消费的端口或寄存器**——存在但不参与功能，预期语义待确认
2. **由外部决定、本模块只能采样的行为**——队列更新延迟、握手信号的生成条件
3. **未定义编码与未覆盖分支**——会在什么情况下出现，取决于谁
4. **推导值的前提**——第 8 章那些"最多 N 拍"依赖什么假设

另有四类**代码里根本没有**的需求侧信息（需求编号、算法语义、频率与跨域策略、取舍理由），按 5.2 处理：**给候选、标 `TBC`、指 `Q-xx`，不留空**。这四类恰恰是客户最想看的——他能一眼看出你哪里理解偏了。

正文里也要就地标记：在这类结论后面写 `(RTL 未明确)`，别只靠附录兜底。两处必须对得上——附录里有的，正文里能找到落点；正文里标了的，附录里有条目。

## 三、多模块单文档的排版细则

留在同一份文档时的固定结构（编号只为示例，层级关系才是要求）：

```
1 文档信息
2 功能描述
3 架构设计
  3.1 顶层结构图与数据流
  3.2 模块划分与职责边界        ← 一张表：模块 / 职责 / 不做什么 / 责任人
  3.3 模块 A
      3.3.1 职责
      3.3.2 端口表
      3.3.3 时序契约
      3.3.4 状态机
      3.3.5 实现方式
      3.3.6 异常与复位
  3.4 模块 B（同上六节）
4 寄存器与配置
  4.1 地址段分配
  4.2 全局控制寄存器
  4.3 模块 A 寄存器
  4.4 模块 B 寄存器
5 接口定义
  5.1 对外接口（本 IP 顶层端口）
  5.2 模块间接口（内部握手，按连接对分小节）
6 验证方案（设计侧交接：范围 + FP/VP + 基线声明）
7 闭环完整性
8 可测性与可制造性设计
附录
```

三条硬规矩：

**一、模块六要素固定成六个三级标题，不许写成散文段落。** 六节里只有两处允许写句子：**「职责」**（一句话 + 明确不做什么）与**「状态机」的跳转原理**（3–5 句，见 3.b），其余必须是表、图或编号列表。这条能挡住大部分"看起来写了但没法验"的内容。评审时缺一节直接判偏弱，不用读内容。

**二、第 3.2 的职责边界表先写。** 模块划分没定清就往下写，等于在流沙上盖楼。表里必须有不做什么——只写做什么，边界永远不会清楚。

**三、编号与图表带模块前缀。** 图 `图 3-A-02`、表 `表 4-B-01`。多文档并存时，光说"图 3"无法沟通。

**四、模块内有多个时钟域时，按域分小节。** 时序契约必须逐域写，因为跨域那句话在哪个域下都不成立：

```
3.3 模块 A
    3.3.1 职责
    3.3.2 端口表            ← 每行必须标时钟域列
    3.3.3 时序契约
          3.3.3.1 aclk 域   ← 本域内的拍数、反压、流水深度
          3.3.3.2 mclk 域
          3.3.3.3 跨域路径  ← 单列一节，逐条写同步方案
    3.3.4 状态机           ← 状态机若跨域，每个域各一张，并标哪张是主
    3.3.5 实现方式
    3.3.6 异常与复位       ← 每个域各写一段复位行为
```

三条要求：
- **端口表必须有 clock domain 列**，不能只在文字里说"这些信号属于 mclk"
- **跨域路径单列一节**，写清：源域 / 目的域 / 信号宽度 / 同步方案（两级同步 / 格雷码 / 异步 FIFO / 握手）/ 是否有数据一致性要求
- **多 bit 信号不允许"各自两级同步"**，必须走格雷码、异步 FIFO 或握手；单列这一节的目的就是让这个判断有地方落笔

只有一个时钟域的模块，不要为了形式拆出 3.3.3.1——**单域就写一节**，标题里注明 `（aclk 单域）` 即可。

## 四、多份 spec 汇总成系统级

**汇总绝不是按子模块分章。** `1 模块A介绍 / 2 模块A接口 / 3 模块B介绍 / 4 模块B接口…` 是把几份文档装订在一起，不是系统级 spec——读者想知道启动时序怎么走，得翻遍每一章。

**系统级只回答跨模块的问题**，按横向维度组织：

| 章 | 写什么 | 不写什么 |
|---|---|---|
| 文档信息 | 下级文档索引表（含各自评审阶段） | — |
| 功能 | 整系统的应用场景、顶层功能编号 | 子模块内部功能列表 |
| 结构 | 一张拓扑图 + 互连矩阵（谁连谁、带宽、协议） | 任何模块内部框图 |
| 契约矩阵 | 模块×模块的接口：方向/位宽/协议/时序拍数/反压 | 模块内部状态机 |
| 时钟复位 | 全局几个时钟域、几个复位域、跨域在哪、同步方案集中列 | 模块内部无跨域的时序 |
| 地址映射 | 段分配表（模块 / 起止 / 大小 / 是否可访问） | 模块内部寄存器明细 |
| 跨模块场景 | 启动与复位序列、错误传播、低功耗进出、性能压测的整链时序图 | 单模块单元测试 |
| DFT/功耗 | 全局 scan 结构、power domain 划分、isolation 需求 | 模块域内配合细节 |

**契约矩阵是这份文档的核心**，也是最容易被省掉的一节：

| 源模块 | 目的模块 | 信号组 | 方向 | 位宽 | 协议/握手 | 时序拍数 | 反压机制 | 约束级别 |
|---|---|---|---|---|---|---|---|---|
| DMA | Crossbar | 写数据 | A→B | 256 | valid-ready | 3 拍 | ready 反压 | **M** |
| NPU | DMA | 描述符完成 | A→B | 1 | valid-only | ≥2 拍 | 无 | **R** |

**最后一列是必须的，也是常被漏的。** 拍数写了却不写它是硬性还是参考，验证就会漏项、集成就会扯皮：

| 级别 | 含义 | 验证怎么做 |
|---|---|---|
| **M**（Mandatory） | 硬约束，实现必须满足 | 必须写断言，违例即 fail |
| **R**（Reference） | 典型值，允许实现优化 | 只做延迟上限检查，记录实际值 |
| **X**（Don't care） | 无时序要求 | 不检查 |

判断标准很实际：**这个拍数被写进过性能预算或对外承诺吗？** 是就 M；只是设计时照着做的大致节奏，就 R。一张矩阵里如果所有行都是 R，说明没人真的用过这张表。

**每个数字必须能指到来源。** "总带宽 512 GB/s"后面接"由 3.4 互连矩阵推导，见附录 B"，否则评审没人验得了。

**引用而不复制。** 子模块的寄存器明细、状态机、内部时序一律给文档编号 + 章节号，不搬正文——复制即漂移。

**只写"删掉会让某个模块做错事"的话。** 判断方法：这句话删掉之后，某个模块的设计者会做错事吗？会 → 该写在系统级；不会 → 属于模块自己的文档。

## 五、逆向补文档（RTL → spec）

**前提必须写在最前面**：RTL 已经存在，文档只能描述它，**对本次实现而言**它永远是记录，不能反过来约束已经写成的代码。它不能用来应付"设计文档评审"——评审看的是当时的设计依据，不是事后追认。

但**记录不等于废纸**。反向文档有两个正当用途：

| 用途 | 服务谁 | 要写到多细 |
|---|---|---|
| **归档档**：寄存器使用、端口与接口、验证的状态覆盖 | 驱动/软件、集成、验证 | 表为主体，第 3 章压缩 |
| **交接档**：接手的人要敢动这份代码 | 后来接手的维护者 | 写到决策层，第 3 章不压缩 |
| （转正后）**契约**：签发给下一轮修改 | 全部下游 | 见 5.8 的转正流程 |

**两档的区别不在章节，在填充深度。** 骨架一律与正向文档相同（5.3），这样两份文档能并排比对，也能从归档档增补成交接档，不必重写。

写之前先看 5.6 的执行顺序（九步），它比章节顺序更重要。

### 5.1 三类字段：什么能当事实写，什么必须标待确认

每一栏都要带出处标记，读者才知道能不能引用：

| 标记 | 含义 | 典型字段 | 怎么核实 |
|---|---|---|---|
| `measured` | 直接取自 RTL，可逐行核对 | 端口名与方向、位宽、参数默认值、地址译码、状态图 | 回到代码逐条对 |
| `inferred` | 提取器推断或人工推导，需确认 | 接口协议类型（AXI4 / Lite / Stream）、模块角色、时钟域归属、频率上限、跨域方案 | 找设计者或看协议信号全集 / 约束文件 |
| `TBC` | 已给出候选，等一句话确认（**必须指 `Q-xx`**） | 需求编号、验收判据、算法语义、取舍理由 | 去 PRD / RTM / 设计者 |
| ~~`tbd`~~ | **不用于反向档内容行** | — | — |

**`measured` 不等于"已穷尽"。** 它只代表"取到的这部分是对的"，不代表没有漏。提取器覆盖不到的写法（宏封装译码、非规整命名的复位、双进程状态机）会静默漏掉，漏掉的部分同样会被标成 measured。所以逆向文档必须附一份**已知限制 + 需人工复核清单**，且清单要具体到"哪个地址的复位值没取到"。

### 5.2 四类补不出来的内容：给候选，不留空

**这一条改过两次，现在是对的：** 代码里读不出需求来源、算法意图、频率策略、取舍理由，但**这不等于可以留空**。客户交 RTL 过来的目的是拿到一份能评审的文档，留空等于把工作原样退回。危险程度是三档：

| 做法 | 后果 | 判定 |
|---|---|---|
| 当事实写、不标记 | 下游当契约用，错了无声 | **最危险** |
| 留 `TBD` 空着 | 交付物有空洞，客户收到半份文档 | **不算交付** |
| 给候选 + 标等级 + 指问题编号 | 审阅人一句话即可确认或否定 | **唯一可接受** |

| 缺什么 | 为什么 RTL 里没有 | 这一栏写什么（**不许空**） | 去哪儿核 |
|---|---|---|---|
| 需求编号与验收判据 | 代码里不含需求来源的痕迹 | `REQ-xxx` 候选 + 反推出的行为描述 + `TBC` | PRD 条款、需求跟踪矩阵（RTM） |
| 算法 / 描述符语义 | 代码写"怎么做"，不写"为什么这么定义" | "代码表现为 X"（不断言意图）+ `[?Q-xx]` | 架构文档、验证环境的参考模型 |
| 时钟频率与跨域策略 | 频率在 SDC 里；跨域实现要判断是否刻意设计 | "按实现推断的上限 / 同步方案" + `inferred` + 若不同的影响范围 | 约束文件、设计者确认 |
| 架构取舍理由 | "当时为什么不选另一个方案"从来不在代码里 | "最可能的理由 + 备选方案" + `inferred`（语气可弱：`可能出于…`） | 决策记录、评审纪要、当事人 |

**为什么"语气更弱"也是合格交付**：候选可以被一句话否掉，空着连否的对象都没有。审阅人回"不对，当时是因为功耗"的成本，比回"这块你补一下"低一个数量级——而后者正是留空造成的。

**裸 `TBD` 零出现，只有两种替代写法**（注意：下面两种都**不是** `TBD`，别读成"这两处可以写 `TBD`"）：① 该字段确实不属于本模块（如频率由 SoC 约束决定）→ 写"由 XX 文档给出"；② 候选已进问题清单且标为阻塞 → 写 `TBC－见 Q-07`。**自检时对 `TBD` 应零命中**——包括这两种位置。

### 5.2.1 找不到设计者怎么办：先给判断，再留问题

现实里最常见的不是"设计者在旁边可以问"，而是**作者已离职、转组、或只肯回答问题不肯写文档**。这时不能停在这里等，也不能硬编，做法是：**先按最可能的假设填一版，把不确定的变成可被一句话回答的问题。**

**只问不猜的文档是废的**——通篇 `TBD` 读者不知道能信什么；**只猜不问的文档是危险的**——推测被当成事实引用。折中是"给出判断 + 标注置信度 + 留可回答的问题"，让审阅人只需回"确认 / 否认"，回答成本从写一段话降到回两个字。

问题清单是**一等交付物，不是附录里的一句话备注**。每条固定六列：

| 编号 | 问题 | 本版默认判断 | 影响范围 | 谁能答 | 级别 |
|---|---|---|---|---|---|
| Q-03 | `awlock` 输入未被消费：有意不支持 locked 传输，还是待实现？ | 判为"不支持"，功能表按 `条件支持` 写 | 2.2 功能表、FP-07 | 原作者 / 协议负责人 | **阻塞** |
| Q-11 | 缓冲深度 8 是算法要求还是面积妥协？ | 推定为面积妥协，进 3.c 决策台账 | 3.a 资源账 | 设计者 | 重要 |
| Q-19 | 保留位 `[15:8]` 读回 0 是设计还是巧合？ | 判为设计（有显式复位赋值） | 4.2 主表 | 任何人 | 记录 |

三个级别的门槛必须一致，否则级别失去意义：

| 级别 | 判据 | 不解决的后果 |
|---|---|---|
| **阻塞** | 不回答，验证就给不出预期值；或功能是否成立无法判定 | 相关 FP 不能进基线，文档标"未就绪" |
| **重要** | 影响可信度与方案评价，但不挡交付 | 文档可用，相关段标注"待确认" |
| **记录** | 只是想知道，不影响任何判定 | 无 |

**留问题的四条纪律：**

1. **正文就地标 `[?Q-03]`**，与清单双向索引。沿用附录 E 原有的双向倒查纪律（见 `review-checklist.md` 一·B「问题清单」组），只是把"未明确"升级为"可回答"。
2. **每条必须带"本版默认判断"**。没有默认判断的问题，等于把工作推回给读者。
3. **回答后只改受影响段落**，条目改标 `已确认（vX.Y，答复人）` 并保留，不删——与"FP 编号不删"同一道理，否则下一个接手的人会重新问一遍。
4. **文档开头必须声明证据状态**：本版由 RTL 反推，未经设计者确认，N 条阻塞问题未解决。这不是免责声明，是给读者的信任等级。

> 问题清单同时是**知识抢救工具**。作者要离职时，拿着清单去问，比"请你写份文档"现实得多——前者是十几个具体问题，后者是一周工作量。

### 5.3 一套骨架，两种填充：目录必须与正向对齐

**不要为了"八章齐备"把每章都填满**——那正是评审最反感的东西。但**也不要删章**：删章会让反向文档和正向文档没法并排比对，也没法后来增补成交接档。

正确做法：**章节与正向文档完全一致，差别只在每章的填充深度与证据标记。**

| 章 | 归档档 | 交接档 | 证据等级常态 |
|---|---|---|---|
| 1 文档信息 | 齐备；状态写 **As-Built**；1.1 记源 RTL 版本与提交号 | 同左 | `measured` |
| 2 功能描述 | 2.2 功能表为主体（三态 + 分级 + 验收判据）；2.1 应用场景写"待确认"并指到问题清单 | 补 2.3 框图、2.4 模式矩阵 | 功能表 `measured`，分级 `inferred` |
| 3 架构设计 | 层级图 + 模块职责表；3.c 决策台账尽量填，3.d 可观测出口**必须填**（验证的抓手） | 3.a 四要素 + 算子表 + 资源账 + 精度口径全填；3.b 三张表 + 原理都要 | 3.a 多 `measured`；3.b 三张表 `measured`、原理 `inferred`；3.c 多 `TBC` |
| 4 寄存器与配置 | **主体**，一张主表（绝对地址）+ 段分配，末列补 evidence | 同左 | `measured` |
| 5 接口定义 | **主体**，端口表 + 协议类型（标 `inferred`），末列补 evidence | 同左 + 通道表 | 端口 `measured`，协议 `inferred` |
| 6 验证方案 | 6B 验证基线（三态清单 + FP/VP + 基线声明） | 同左 | 随 FP |
| 7 可测性 | 只记 RTL 可见的 DFT 端口与低功耗单元，其余写"见 DFT 单独文档" | 同左 | `measured` |
| 附录 A/B | 按 706 行的生成纪律，有流程才设 | 同左 | — |
| 附录 E | **升级为问题清单**（见 5.2.1），归档档必填 | 必填 | — |

**空章节不许留白**，必须三选一：`本模块不适用`（给理由）/ `TBC－见 Q-07`（候选已给、待确认）/ `由 XX 文档给出`（给文档名与版本）。留白会被当成遗漏，写字会被当成已覆盖。

**裸 `TBD` 不在三选一之列。** RTL 既然在手上，文档里就不该出现"这里我没写"的格子——`TBD` 和"留白"只差一个字符，对读者的效果一样：这一格空了。区别只在留白是疏忽、`TBD` 是自觉的疏忽，**后者更糟，因为它让人以为已经处理过了**。写法见 5.2，自检时对 `TBD` 应零命中。

**第 3 章是两档的分水岭。** 归档档压缩它是对的——驱动和验证不关心流水级数；交接档压缩它就错了——接手的维护者要改代码，必须知道决策与理由。**判断该写哪档只看一个问题：读完这份文档的人敢不敢改这段 RTL？**

### 5.3.1 反推文档的三条读感纪律

机器拼出来的文档最容易"结构全对，读起来不像人写的"。三个具体成因，各有对策：

| 病 | 表现 | 对策 |
|---|---|---|
| **顺序跟着代码走** | 文件 → 模块 → always 块 → 信号 | 正文顺序跟**数据流**走：输入 → 处理 → 输出 → 异常。代码顺序是组织方式，不是叙述顺序 |
| **篇幅均匀用力** | 每节都三段，P0 和 P2 一样长 | 按分级配篇幅：P0 详写、P2 一句带过。均匀用力是机器痕迹最重的地方 |
| **追溯信息打断阅读** | 正文里夹"（见 foo.sv:123）" | 全部收进 evidence 列或脚注，正文只留结论 |

**两个验收动作，做完才知道像不像人写的：**

1. **复述测试**：把文档交给没读过这段 RTL 的人，让他复述"这个模块做什么"。三个观察点——复述里出现信号名 → 名字漏进正文了（见 5.3.2）；说不出"为什么需要这个模块" → 职责没写；说得出做什么但说不出什么时候会出错 → 异常与边界缺失。
2. **审核者工作流测试**：审核人要能按固定顺序逐格打勾，而不是通读散文。推荐顺序：**先回答问题清单 → 再看功能表（判粒度）→ 再看寄存器/接口表（对数值）→ 最后看决策台账（补理由）**。文档的组织方式应当支持这个顺序，即问题清单放最前、功能表紧随其后。

### 5.3.2 名字只住在表里：正文不许有内部信号名

**一条规则：真实名字只出现在表里，正文只出现概念名。**

| 位置 | 处理 |
|---|---|
| 端口表、寄存器表、状态编码表、参数表 | **必须用真实名**——这是交付价值所在，驱动和集成要照着这些名字写代码 |
| 正文散文、框图、功能表、决策台账 | **一律概念名**：`reg_tx_wr_ptr_gray` → "写指针（格雷码编码）" |
| 1.2 术语表 | 建映射：概念名 ← 真实名（一对多，一个概念可能对应多个信号） |
| 波形图 / 时序图 | 允许端口名——可裁决判据要求能指到具体信号。内部信号用概念名，图脚注明对应关系 |

**极少数允许出现代码的地方**，只有三处，因为自然语言在那里注定不精确：

- 参数化位宽公式：`WIDTH = clog2(DEPTH)`
- 寄存器位域拼接：`{mode[1:0], addr[9:0]}`
- 状态编码值：`IDLE = 3'b001`

**绝对禁止**：always 块片段、赋值语句、源码行号混在正文里。

**可自动化的判据——内部信号名密度**：生成后拿端口名 + 寄存器名 + 参数名做白名单，扫描正文里所有 `snake_case` / `camelCase` 标识符，凡不在白名单的就是内部信号名，逐条消。经验线：**一个模块的正文里出现超过 5 个未解释的内部信号名，就不是文档，是代码的另一种排版。** 1.2 术语表里登记过的概念名不计入。

### 5.4 写完之后的自查

**两个方向都要自查，不是只有反向才查。** 早先这一节只对 RTL → spec 的产物，正向文档写完反而没人管——这是个双标：反方向因为它难，所以有人盯着；正方向因为看着顺手，就默认它没问题。实际上正向文档的错误更贵，它会被下游当成需求基线。

**分工要说清**：本节只列**写作过程**的检查项（顺序、篇幅、名字、可读性——这些是表格判不出来的）；**表格与契约的正确性**（offset、位域、位宽、编号族、`TBD`）全部归 `review-checklist.md` 第一节的 66 条，**交付前逐条过，不在这里重抄一遍**。重抄的结果一定是两份漂移——这一节**早先**就犯过这个错：自己长出了一份 26 条的清单，其中 7 条与清单重复、措辞还不一致（**该份已删除**，条目已并入清单）。

**机器能判的先交给机器**：`python scripts/spec_lint.py <spec>.md` 覆盖 offset/位域/位宽/段/`TBD`/必备件/端口/编号族共 38 条规则，输出带行号。**先跑到"可确证"栏归零，再来过本节与清单**——那批事情靠读发现不了（200 行寄存器表里的位域重叠、同 offset 少一个字母的命名），而脚本 1 秒出结果。它判不了的判断项才是本节和清单存在的理由。

#### 5.4.1 正向文档（PRD → spec）

**分三次查，不要留到最后一次性过**——最后一次只能查格式，改不动方案了。

**① 骨架刚立起来时（约 30%）**：只查结构，别碰内容。

- [ ] 八章齐备；裁剪的章节在 1.3 记了原因，不是悄悄少一章
- [ ] 1.0 文档控制区有编号、密级、状态、生效日期、主笔/复核/批准、分发范围
- [ ] 1.2.1 编号族总表已建（十类前缀各归其位，没有同号不同物）
- [ ] 拆文档的粒度按四条判据走过（责任人 / 交付节奏 / 评审场合 / 版本演进），不是因为"子模块多"就拆
- [ ] 多模块单文档按 3.x 分节，模块六要素是六个三级标题而非散文
- [ ] 每章有责任人（不只全文一个）

**② 第 3、4 章落笔后（约 70%）**：这里查的是"想清楚没有"。

- [ ] **正文顺序跟数据流**：输入 → 处理 → 输出 → 异常。如果顺序跟的是代码文件顺序，说明还在按实现写，不是在写设计
- [ ] **篇幅按分级分配**：P0 详写、P2 一句带过。每节都三段是均匀用力，也是机器痕迹最重的地方
- [ ] **决策台账的"失效条件"一列无空**：空着的那一行，三个月后没人敢动它
- [ ] **可观测出口表写明了哪些内部状态"看不见"**，且给了间接推断路径
- [ ] 状态机三张表齐备（转移表带判定顺序与显式兜底行 / 状态×输出矩阵 Moore、Mealy 分开 / 不变量 `INV-xx`）、跳转原理 3–5 句照写
- [ ] 算子表的复用次数 × 并行度能倒推回架构预算；倒推不回去说明方案与预算脱节
- [ ] 第 6 章每句话都是设计者能独立负责的（"采用 UVM 环境"这种就不是）

**③ 交付前**：先跑 `review-checklist.md` 第一节，再走这三项。

- [ ] **散文占比**：单节 ≤3 句（跳转原理与"职责"除外）；超三成的章节要单独说明为什么不能表格化
- [ ] **复述测试**：交给没参与过的人，让他复述"这个模块做什么"。说不出"为什么需要它"→ 职责没写；说得出做什么但说不出什么时候出错 → 异常与边界缺失
- [ ] **审核者工作流测试**：能按固定顺序逐格打勾（先功能表判粒度 → 再寄存器/接口表对数值 → 最后决策台账补理由），而不是通读散文

**正向特有的一个坑**：因为没有 RTL 可对，`TBC` 会比反向档多得多，很容易一路标下去就交付了。判据是——**每个 `TBC` 必须指到一条 `Q-xx`，每条 `Q` 必须有答复人或明确的"本项目按此判断执行"**。没有答复人的 `TBC` 不是待确认，是没做决定。

#### 5.4.2 逆向文档（RTL → spec）

**逐条清单不在这里重抄，看 `review-checklist.md` 的「一·B、反推稿专项检查」**——那里是单一来源，共 45 条，按档位与骨架 / 问题清单 / 证据等级 / 读感 / 名字痕迹 / 功能粒度 / 第 3、6 章完整性分组。这一节**早先**另有一份 26 条的清单，与那边 7 条重复、措辞还不一致（**该份已删除**，其余 18 条已全部并入）。**进场前先跑 `scripts/spec_lint.py`**：反向档的位域表是从代码抄来的，重复 offset 与区间相交靠读发现不了。

本节只留**三个写完才知道的动作**，它们是过程性的，清单里判不了：

1. **复述测试**：交给没读过这段 RTL 的人复述"这个模块做什么"。出现信号名 → 名字漏进正文；说不出"为什么需要这个模块" → 职责没写；说得出做什么但说不出什么时候出错 → 异常与边界缺失。
2. **审核者工作流测试**：审核人要能按固定顺序逐格打勾——**先回答问题清单 → 再看功能表（判粒度）→ 再对寄存器/接口数值 → 最后看决策台账（补理由）**。组织方式不支持这个顺序，说明问题清单没放最前、或功能表被埋在第 5 章之后。
3. **反向特有的一条自查**：把正文里每条"X 发生"翻回代码，问"这一句是读出来的，还是推出来的"。**读出来的标 `measured`，推出来的标 `inferred`**——反向文档最贵的错误不是漏写，是把推断标成了实测，下游不会去核对一个标着 `measured` 的结论。

### 5.5 一份判据：这份 as-built 值不值得写

不是所有 RTL 都值得逆向成文档。满足以下两条以上才值得投入：

- **有人要接手或集成**：驱动团队、集成团队、后来接手的维护者，他们读 RTL 的成本高于读一份表
- **寄存器数量可观**（比如 > 10 个地址）：端口表和寄存器表能省下大量翻代码时间
- **接口协议需要对外说明**：对方要按协议接，不能让他去猜 `awvalid` 的时序

反过来，如果一个模块只有几个信号、没有寄存器、接口是内部临时线——直接读代码更快，写文档是浪费。

### 5.6 执行顺序与增量回填

**章节顺序不等于写作顺序。** 按下面九步走，能少返工：

1. **定范围**。顶层模块、要展开的子模块层次、是否含第三方 IP（含第三方时该段标"外部交付，见 XX 手册"，不展开明细）。
2. **先只读端口与寄存器列表，写下功能候选**（不看实现）。这一步反直觉但最有效，理由见 5.7——读完代码再列功能，列出来的必然是代码结构。
3. **通读一遍，先写底稿不写正文**。建三张表：端口清单（名/方向/位宽/时钟域猜测/是否被引用）、always 块与状态编码、参数与宏清单。这三张表决定后面能写到多细。
4. **对第 2 步的功能候选做三级筛**（5.7），过筛的进功能表，未过的分流到 3.a / 3.d / VP。
5. **从端口表倒推第 5 章**。逐个信号查引用次数：0 次的标"存在但未参与功能"，进附录 E；只在敏感列表出现的同样处理。
6. **从赋值路径倒推第 4 章与第 2 章**。先定位写清路径再填 attr/reset，别按名字猜。功能表此时才填支持状态与分级。
7. **从状态编码倒推第 3 章状态机与第 8 章时序**。状态机做闭环检查；时序场景只写代码能支撑的拍级顺序，标推导前提。
8. **打 P0/P1/P2 分级**。这一步不能省——第 6B 的 FP/VP 直接继承这个分级，没分级就等于把验证优先级交给验证方猜。
9. **最后写第 6B 章与附录 E（问题清单）**。这两处是全篇的收敛点，放最后写才不至于反复改。第 6B 的 FP/VP 按 `references/fp-vp-generation.md` 生成。

**交付前反向验一遍**：从问题清单的每条倒查正文有没有落点，从正文每个 `[?Q-xx]` 倒查清单有没有条目。两个方向都通才交。

**增量回填（交付后 RTL 又改了）**：不必整篇重写。先做 diff 定界——只回填受影响的章节，修订记录里写"哪些章节对应哪次提交"。FP 编号不改、新增追加号、废弃标注保留；**若改动触及某 VP 的预期值来源，该 VP 标"存疑"并单独列出**，通知验证方基线的失效范围。ECO 不升大版本号，只升修订号（如 v1.2 → v1.3）。

### 5.7 反向功能点怎么切：与正向粒度对齐

**这是反向文档最容易做错、也最难事后补救的一步。** 错法是按代码单元切——一个 module 一条、一个 always 块一条、一个寄存器字段一条。切出来的是"代码结构清单"，验证拿着它去测，测的是实现细节，不是功能。

根源在于取证方向不同：**正向功能的来源是需求条目，反向功能只能从"外部可观察的行为差异"倒推**。所以不能从结构枚举，要从端口行为枚举。

#### 三级筛：过三问才算功能点

| 筛 | 问题 | 不过的怎么处理 |
|---|---|---|
| ① 外部可观察 | 只看端口与寄存器读回，能不能判定它成立？ | 不能 → 它不是功能，是内部状态。归 3.d 可观测出口 |
| ② 实现无关 | 流水换两级、仲裁换策略、FIFO 换成寄存器堆，这条描述还对不对？ | 不对 → 它是实现选择，不是功能。归 3.a 实现方式 |
| ③ 可独立判对错 | 这一条能不能被单独判错？发现一半对一半错，就该拆 | 不能拆开判 → 与其他条目合并，或它是同一功能的变体 → 归 VP |

三条都过的，才是功能表里的一行，并且**这行的列结构与正向文档完全相同**（id / 功能 / 支持状态 / 分级 / 验收判据 / 说明，共 6 列）。**不要加"反向专用列"**——出处信息进 evidence 列，不进功能表，否则反向表 7 列、正向表 6 列，永远没法并排审。

#### 过细：把实现方式当成了功能

| 反例（错法） | 正解 | 错在哪 |
|---|---|---|
| "`tx_fifo` 使用 8 级同步 FIFO" | "发送缓冲深度可配置，满时反压上游" | 结构不是功能 |
| "状态机有 5 个状态，IDLE→WR→WT→RD→IDLE" | "一次事务分启动、写入、等待、读取四阶段可完成" | 状态是手段，阶段是行为 |
| "`cnt[7:0]` 每拍加 1" | "字节计数器到阈值后产生完成脉冲" | 计数器是实现，计数含义是功能 |
| "`shifter` 右移 3 位" | "支持 1/2/4/8 字节对齐的地址计算" | 位移是实现，对齐能力是功能 |
| 一条 FP = 一个寄存器字段 | 一条 FP = 一个可独立判对错的行为 | 字段清单不是功能点 |

#### 过粗：把多个功能塞进一条

判据与正向完全一致：**这一条能不能被单独判错？** 能，就是一条；发现"一半对一半错没法判"，说明它里面至少装了两个功能。典型过粗项是"支持 AXI 主机接口"——里面至少含读写通道独立、outstanding、错误响应、边界对齐四件事。

#### 命名：动词 + 对象 + 条件

- 对：`FP-03 突发长度超过阈值时拆分事务`
- 错：`FP-03 dma_split_fifo 处理逻辑`（这是模块名，不是功能）
- 错：`FP-03 支持 AXI4`（这是协议名，里面装了四五个功能）

#### 粒度校准锚点（报警线，不是标准答案）

一个中等复杂度模块（1000–3000 行、3–8 个子模块），FP 数量落在 **10～40 条**：

| 数量 | 说明 | 怎么办 |
|---|---|---|
| < 8 条 | 基本是按模块切的，过粗 | 回到三级筛的第三问，往下拆 |
| 10–40 条 | 正常区间 | — |
| > 60 条 | 基本是按字段/分支切的，过细 | 看有没有混进实现方式，按反例表逐条重写 |

出了区间先回头查切法，不要改判据去迁就。**这个数唯一的作用是报警**——真实模块复杂度差异很大，落在区间外的正当理由要在 1.3 行文规范里写一句。

#### 一条硬纪律：先抛开 RTL 写功能候选

读代码之前，只看着端口与寄存器列表，写下"这个模块应该能做到哪些事"。写完再读代码逐条对照，会得到两个副产品：

- **代码里没实现的** — 正好是功能缺口。这是意外收获，验证最需要，应进问题清单而不是悄悄丢掉。
- **代码有但你没写出来的** — 说明你的功能视角有盲区，回头补。

这是唯一能主动抵抗"结构决定功能"的办法。跳过这一步，后面三级筛筛得再细，候选池本身已经是按代码结构生成的。

### 5.8 从记录转正为契约

反向文档的"不能应付评审"说的是**评"当时设计对不对"它没资格**。但它可以合法地转正，路径有四步：

| 步 | 做什么 | 谁做 |
|---|---|---|
| 1 | 回填稿 = 事实底稿（`measured` 事实 + 问题清单） | 反向工程师 |
| 2 | 补决策理由：问题清单的阻塞项与重要项逐条落实，补不上的书面声明接受 | 设计者 / 主管 |
| 3 | **开文档评审——评的不是"当时设计对不对"，而是三件事**：事实是否属实、缺口是否诚实、理由是否补齐 | 评审组 |
| 4 | 评审签发、版本冻结 → **对后续每一次修改，这份文档恢复契约身份** | — |

**第 4 步是全部价值所在。** 签发之后，规则回到正向：改 RTL 先改文档，或走偏离登记（1.1.1）。交接场景的价值恰恰全在签发之后——新人接手那天起，这份文档就是他动代码之前的契约。

转正的**准入清单（七条可勾选）**，缺一条就不能改状态：

| # | 准入条件 | 怎么证明 | 谁确认 |
|---|---|---|---|
| 1 | 阻塞级问题已清零 | 附录 E 无 `阻塞` 未关闭项 | 反向工程师自证 |
| 2 | 已接受的未关闭项有书面记录 | 每条写了"接受人 / 日期 / 风险" | 主管 |
| 3 | 第 3 章到交接档深度 | 3.a 四要素 + 3.b 三张表 + 3.c 含失效条件 | 评审组 |
| 4 | 3.e 核对表无未处理的 `文档需修正` | 每行结论为 `一致` 或已修复 | 反向工程师自证 |
| 5 | `TBD` 零命中、`TBC` 全部可追溯 | 每处 `TBC` 指 `Q-xx`，每条 `Q` 有答复人或接受记录 | 评审组 |
| 6 | 需求追溯不再是"评审议程" | 7.1 标题不含"未建立追溯"，至少一条 `REQ` 已 `已确认` | 评审组 |
| 7 | 文档状态已改、1.1 记签发人与日期 | 状态写 `已签发 vX.Y`，不是 `As-Built` | 签发人 |

**第 6 条最容易被含糊过去。** 一份需求全部 `TBC` 的文档，事实部分可以很扎实，但它**没有追溯链**——签发它等于宣布"这份文档后面不会有需求变更引起的返工"。所以只要 7.1 标题还挂着"评审议程"，就不许签发，哪怕其余六条都满足。

**不要跳过评审直接改状态。** 没有评审的转正只是自我声明，下一个接手的人分不清哪些是事实、哪些是某人猜的——这比老老实实标 As-Built 更危险。

### 5.9 规范性动词：哪些句子有约束力

文档里"必须""应该""可以"混用时，读者无法判断哪句是硬要求、哪句是建议。**一份会被当契约引用的文档，必须先把这几个词定死。**

| 动词 | 效力 | 用在哪 | 违反的后果 |
|---|---|---|---|
| **必须 / 不得 / 禁止** | 规范（normative） | 契约条款、约束、接口要求 | 实现不符即缺陷，须走变更评审 |
| **应 / 不应** | 规范，但允许有理由的偏离 | 默认做法、推荐结构 | 偏离须在 3.c 登记理由与失效条件 |
| **可 / 可以** | 非规范（informative） | 实现自由度、可选优化 | 无后果，不构成契约 |
| **说明 / 示例 / 推断** | 非规范 | 解释、举例、候选 | 无约束力，不得被引用为要求 |

**两条落笔纪律：**

- **一条契约只用一个动词，不叠用。** "应必须""建议必须"这类叠加句，读者只能自己挑一个信——那等于没写。
- **非规范内容必须显式标注。** 段落标题加"（说明）"/"（示例）"，表格上方加"以下为推断，非要求"。不标的话，读者默认整篇都是规范——**而反向文档里绝大多数句子是描述、不是要求**，这是最容易造成误解的地方。

> **反向档的特殊性：整篇默认非规范，它是记录。** 只有 3.e 判为 `一致` 的事实、以及签发后经客户确认的条款，才具备规范效力。这一点要在文首说清，不能指望读者从"状态：As-Built"自己推出来——多数读者根本不知道 As-Built 意味着什么。

## 阶段评审的判定口径

先分阶段再判定，不同阶段查的东西不一样：

| 阶段 | 必须齐备 | 允许还缺 |
|---|---|---|
| 50% | 骨架八章 + 寄存器/接口契约表 + 功能列表初稿 | 图、时序细节、分级 |
| 85% | 模块六要素 + 四类图 + 功能表三态与分级 | 边界场景、附录 E 完整性 |
| 100% | 全部内容 + 附录 E + 双向倒查通过 | 无——缺任一项即不通过 |

阶段没到就按 100% 的标准挑毛病，评审会变成挑格式；到了 100% 还只查结构，就是放水。

| 判定 | 含义 |
|---|---|
| 通过 | 结构、内容量、关键要素齐备，能指到具体章节 |
| 偏弱 | 有内容但要素不全或明显偏薄，附缺口清单 |
| 不通过 | 章节缺失或为空，附补法 |
| 需人工 | 依赖外部交付件（RTM、caselist、评审纪要），文档内无法判定 |

**不要用字数当"写清楚"的代理。** 实测中正文与图往往不缺，缺的是结构化的接口契约与时序契约——先查这两张表。

**多模块 IP 的优先检查顺序：** 3.2 职责边界表 → 4.1 段分配 → 4.2 主表 → 5.2 模块间接口。这四处齐了，文档骨架就立住了；其余章节的缺陷都是可补的局部问题。
