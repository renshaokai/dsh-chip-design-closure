# 功能点（FP）与验收观察点（VP）生成方法

Spec 写完之后，验证工程师要的不是"读得懂"，是**照着这份文档就能列出用例**。这份文档给的是从 spec 条款到 FP、再到 VP 的转换规则。

> **范围**：本文档是设计侧对验证侧的**交接物说明**。产出到 VP 清单为止——VP 之后（TB、sequence、testcase、断言、coverage bin、跑仿真、覆盖率报告）属验证环境，不在此处。VP 写得越细越好，但它是"该测什么"的声明，不是"怎么测"的实现。

> **VP 是"验收观察点"，不是测试用例。** 它声明的是"什么算对、在哪看"，验证侧据此建验证计划、写 TB 与断言，并有权在清单之外自行扩充。**这个区分要在交付时说出来**——叫"测试点"容易被两边同时误解：设计侧以为在替验证排用例（于是不敢写细），验证侧以为用例已经有人负责（于是不去补）。名字里有"验收"，责任就在设计侧；名字里有"测试"，责任就滑到验证侧了。

适用两侧：

- **正向 spec**：条款来自意图，FP/VP 在评审后即可交付验证，作为验证计划的输入。
- **反向 spec**：条款来自 RTL，FP/VP 是验证工程师的主要抓手，但**必须附带证据等级**——见末节「自证风险」。

## 一套编号，两级结构

| 级 | 名称 | 一个单元是什么 | 数量级 |
|---|---|---|---|
| FP | 功能点 | 一个**可独立判定对错**的行为 | 十几到几十 |
| VP | 验收观察点 | 一个**激励条件 + 预期结果**的组合 | 每个 FP 若干 |

编号一经发布不改。新增用追加号，废弃标注保留不删——验证用例、覆盖率、缺陷单都引用这串号，改了别人对不上。

## 五步生成法

### 第一步：提取需求条款

逐条读 spec，每条记录三件事：**条件 / 操作 / 结果**。同时保留条款在文档里的位置（章节号或表名）。

- 表头、复位要求、配置要求与正文同等对待，不要只提功能描述。
- 一句话里含多个行为的，拆成多条记录，不要合并。
- 读不准的先标"待复核"，不要猜着提炼——猜错的条件会变成错用例。

留痕：`条款编号 / 原文摘录 / 文档位置 / 提取出的条件-操作-结果`。

### 第二步：组织成 FP

**先按章节分组，再合并描述同一功能的条款。**

合并判据只有一条：**同一组条款检查的是同一个"对错"**。按寄存器字段数、按实例个数去数 FP，得到的是字段清单不是功能点。

**反向 spec 的 FP 从行为切，不从结构切**——按 module、always 块、寄存器字段去数，数出来是代码结构清单。三级筛（外部可观察 / 实现无关 / 可独立判对错）与过细过粗的反例对照见 `spec-outline.md` 5.7，做反向 spec 时先过那三道筛再来这里组 FP。粒度报警线：中等复杂度模块 10–40 条。

每个 FP 要能回答四个问题：

| 字段 | 内容 |
|---|---|
| FP 编号 | `FP-<域>-<序号>` 或沿用章节号 |
| 名称 | 动词短语，`中断置位与屏蔽`，不写"中断相关" |
| 行为概述 | 一句话说清做什么 |
| 依据条款 | 对应哪些条款编号，可多条 |
| 分级 | P0 / P1 / P2，见下节 |
| 证据等级 | `measured` / `inferred` / `TBC`（反向 spec 必填；`TBC` 须指 `Q-xx`） |

通用检查（复位、接口时序、时钟域）单独成 FP 并注明依据，不要散进各功能里——散进去之后没人负责整体核对。

### 第三步：分级

按实现依赖排，不按重要性排。这个顺序同时是**验证优先级**：

| 级别 | 含义 | 判定 |
|---|---|---|
| P0 | 基础运行路径 | 缺了它模块根本不能用：复位值、基本事务能否发起与完成 |
| P1 | 完整功能 | 各功能在正常配置下都能工作：各模式、各路径、各分支 |
| P2 | 边界与完善 | 极端值、并发、异常注入、性能相关 |

**P0 未覆盖完，不该去磨 P2 的边界。** 这条要写进交付说明，否则验证会按"覆盖率高就是好"去做，最后 P0 有洞而总体数字漂亮。

反向 spec 的分级还有一层用途：由 RTL 反推时，P2 的边界行为往往最不可靠（很多边界根本没被设计者想过），分级能提示验证工程师哪些 FP 的预期值最需要人工复核。

### 第四步：设计 VP

对每个 FP，先**为每条需求保留一个测试项**，再补配置、操作、预期结果与检查方法。

VP 固定字段：

| 字段 | 内容 | 反例 |
|---|---|---|
| VP 编号 | `FP-xx.y` | — |
| 改变的条件 | 相对基线改了什么 | "测试一下屏蔽" |
| 激励 | 具体驱动什么信号/写什么地址什么值 | "给个事件" |
| 预期结果 | 可判定的值与时序位置 | "irq 应该正常" |
| 检查位置 | 顶层端口 / 内部监视 / 子模块 | 不写 |
| 执行类型 | 定向 / 随机约束 / 异常注入，怎么跑这一条 | 只写"测一下" |
| 依据 | spec 条款号 + 源码位置（反向） | 不写 |

> **"什么必须恒成立"不归 VP，归 INV。** 早先这里放过一列"建议断言方向"，现在迁到 `spec-template.md` 3.3.4 的不变量表（`INV-xxx`）——理由是这个字段装的是**恒真声明**，而 VP 的定义是"给激励、看预期"，两者的判定前提相反。恒真项放在 VP 表里，读者会以为它需要一个激励才能触发，从而漏掉"任何一次运行都必须成立"这层强度。
>
> 判据一句话：**能不问"怎么激励"就判的，进 INV；必须先说"给什么"才能判的，进 VP。**
>
> 边界仍然不变：INV 与 VP 都只到**语义级**（"done 宽度恰为 1 拍"可以），SVA 语句、断言库、绑定方式、覆盖率 bin 归验证侧。**边界不在写不写断言，在写的是"必须恒成立什么"还是"怎么用语法表达它"。**

**预期结果必须落在具体的采样边沿上。** "下一拍 pending 变 1" 和 "pending 会变 1" 是两种质量；后者在时序错一拍时依然"通过"。

### 第四步补：负向 VP 与边界 VP

**正向用例证明"能做"，负向用例证明"不该做的时候没做"。** 后者是缺陷的主要藏身处，而它不会从"正常流程"里自然长出来——必须按条件清单逐条反向生成。

| 从哪来 | 生成什么 VP |
|---|---|
| 每个使能 / 门控条件 | 条件**不成立**时，对应动作不得发生（"使能为 0 时不进启动态""门控关闭时不发起请求"） |
| 每个前提（缓冲非空、握手就绪、状态正确） | 前提缺失时行为是什么：保持、丢弃、还是报错——**三种都算合格答案，没答案不合格** |
| 每个脉冲类输出 | 宽度恰为 N 拍（不是"至少 1 拍"），以及相邻两次脉冲之间的最小间隔 |
| 每个等待态 | 等待的完成信号**永不到来**时会怎样：永久等待、超时退出、还是可被打断——由设计者给答案 |
| 每个"不应出现"的编码 / 分支 | 默认路径是什么（非法状态下一拍回哪），以及是否会自锁 |
| 每个刚被认定的风险 | 一条能**证明风险存在**的用例，先复现再谈修复 |

反向 spec 里还有一类专属负向项：问题清单里判为"疑似缺陷"的条目，各配一条 VP 记录**实际行为**（不是"应如何"），这样 RTL 修了以后，这条 VP 的预期值才需要改——**它同时是缺陷的复现脚本**。

### 第五步：拆分与合并

**只有前提、预期结果、驱动与观察信号、检查方式、执行类型全部一致，才能合并。** 合并后保留需求编号与各组测试数据。

该拆的典型场景：

- **顺序敏感**：先屏蔽后事件 / 先事件后屏蔽，状态相同但输出不同，必须两条。
- **边界值**：`limit=0`（不启动）与 `limit=1`（最短完成）行为不同，各一条；`limit=4` 与 `8` 可共用"N 周期完成"；最大值单独保留。
- **并发**：同拍两个输入都有效，优先级必须单独测。

该合的典型场景：同一检查、只差数据值的参数扫描，合成一条带数据组的 VP。

## 子模块与顶层分工

同一个行为，在子模块测还是顶层测，检查力度不同。这一步在 VP 上就要分清楚，**否则验证侧拿到清单也不知道该搭几套环境**。

| 层级 | 激励入口 | 观察位置 | 查什么 |
|---|---|---|---|
| 子模块 | 直接驱动子模块端口 | 子模块输出 | 本模块逻辑是否正确 |
| 顶层 | 走真实接口协议 | 顶层输出 + 必要的内部监视 | 连接、路由、跨模块时序是否正确 |

写 VP 时的三条规矩：

- **顶层类 VP 要标明"经真实路径"**，写清从哪个端口进、经哪条连接、到哪个输出——不要用"直接给内部信号"描述激励。省事直接驱动内部连线测的是子模块，不是集成。
- **同类的多个实例分别列 VP**，覆盖配置、路径与结果，并单独列一条查实例间串扰。只列一个实例是常见漏项。
- 顶层不可见的信号，在 VP 的"检查位置"列写明**预期从哪里观察**（端口/输出/寄存读回）。具体用监视器还是断言去抓，是验证侧的实现选择，VP 只声明观察点在哪。

## 追溯链（设计侧闭到 VP 为止）

这份文档的追溯到 VP 收口。再往下的 sequence、test、coverage bin 属验证环境，不在设计侧产出范围。

```
spec 条款 → FP → VP        ←── 本文档负责到这里
                  ↓
            用例 → 覆盖率点   ←── 验证侧负责，本文档只提供输入
```

设计侧要查的三条断点，**全是文档自洽检查，不需要跑仿真**：

- 从条款查到 FP：**有没有条款一条 FP 都没进**
- 从 FP 查到 VP：**有没有 FP 只登记没 VP**
- 从 VP 查到预期结果：**有没有 VP 没写清预期值与时序位置**

这三条查完，VP 清单就是完整可交付的验证输入。能不能命中覆盖率，是验证环境的事。

**与验证侧的接口**：交付的 FP/VP 清单里，编号、分级、预期结果三项就是验证侧建 coverage bin 与用例的输入。验证侧按覆盖率缺口回填后，若发现某条已实现行为在 spec 里没有对应条款，那是**反向 spec 的漏记**，反馈到设计侧补 FP——但发现动作由验证侧做，因为只有他们手上有覆盖率报告。

## 交付给验证工程师时的必备声明

不写这段，VP 会被当成保证值用。

1. **适用范围**：本 VP 清单覆盖了哪些 spec 条款，哪些没覆盖、为什么。
2. **分级分布**：P0/P1/P2 各多少条，**哪些 P0 还没有对应 VP**（注意措辞：是"没有 VP"，不是"用例未实现"——用例归验证侧，不在这份清单的声明范围内）。
3. **证据薄弱项**：标 `inferred` 与 `TBC` 的 FP 逐条列出——这些 FP 的预期结果最可能错。
4. **未明确项对照**：附录 E 的每条限制（反向场景即问题清单里的每条问题），对应说明"因此哪些行为无法给预期结果"。

## 自证风险（反向 spec 专项）

**用 RTL 反推的 spec 做验证标准，存在结构性风险：预期结果来自实现，验证就变成用实现验证实现。** RTL 里那个 bug 会被写成"预期行为"，验证器照着检查，永远报通过。

风险不是不能接受，但必须显式管理：

| 做法 | 作用 |
|---|---|
| FP 标证据等级 | `measured` 的预期可信；`inferred` 的要人工确认；`TBC` 的不能作为判定依据，且必须指到 `Q-xx` |
| 引入需求侧来源 | 有需求文档或协议原文时，逐条比对；不一致处标冲突而非择一 |
| 设计者确认 | 未消费端口、异常编码、可疑分支，逐条找设计者签字确认 |
| **没有问题清单就标"未就绪"** | 无设计者可问时，阻塞级问题未清零的 FP 不进基线——它可以列出来，但必须标"未就绪"，不能混进可用清单 |
| 未明确项不作预期 | 附录 E / 问题清单里的项，VP 只能写"记录实际行为"，不能写"应如何" |

**注意一个容易被忽略的自我麻痹：FP 写得漂亮不等于功能切对了。** 如果 FP 是从代码结构切出来的（一个模块一条、一个寄存器字段一条），VP 会写得非常齐全、覆盖率看着也漂亮，但它验证的是实现细节本身——实现改了，VP 全废；实现错了，VP 全过。所以交付前务必回查一遍粒度（`spec-outline.md` 5.7）。

**能力边界说明**：反向 spec + VP 足以支撑**回归基线**与**改动影响分析**——它精确描述了当前实现做什么，改了哪里会影响哪些用例，这已经很有价值。但**需求正确性**的判断不能来自它，那需要独立的需求来源。这个边界要在交付时讲明，不要默认对方清楚。
