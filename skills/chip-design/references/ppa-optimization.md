# PPA 分析与优化

## 1. 先拆，再改

**面积构成**

| 组成 | 怎么看 | 占比高说明 |
|---|---|---|
| 组合逻辑 | cell area - seq - macro | 逻辑太冗余，可资源共享/拆 mux |
| 时序单元 | 触发器数量 × 单位面积 | 流水过碎、寄存器重复、位宽冗余 |
| 存储 | SRAM/ROM 实例（按 bit 数单独算） | 容量或 bank 划分问题，改代码无用 |
| 宏单元/IO | 实例个数 | 接口规格问题，架构层面 |

**功耗分解**

```
总功耗 = 动态 + 静态
动态   = α·C·V²·f（翻转）+ 短路功耗（一般占总动态 10% 内）
静态   = 漏电 ≈ 与面积、阈值电压、温度强相关
```

**α（翻转率）的口径必须与公式配套**，这是最容易算错 2 倍的地方：

| α 的定义 | 配套公式 | 说明 |
|---|---|---|
| 每周期发生 0→1 翻转的**概率**（0–1） | `P = α·C·V²·f` | 本套底稿统一用这个口径 |
| 每周期**电平变化次数**（0–2） | `P = 0.5·α·C·V²·f` | 报里若给的是"toggle rate"，多为此口径 |

`C` 是**该节点全部下游负载之和**。不要再额外乘"活动节点数"——那是重复计数，`C` 已经把节点数包含在内。真要按节点拆，写成 `Σ(α_i·C_i)·V²·f`。

架构层面能改的是 **α（翻转率）** 和 **C（电容/面积）**，改不了 V 和 f（那是工艺与需求定的）。

**性能**

先定位瓶颈是吞吐还是延迟：
- 吞吐不足 → 并行度、流水级数、反压气泡
- 延迟过长 → 关键路径级数、握手往返、存储访问次数

## 2. 找热点

不要平均用力。按收益排序：

1. 面积 Top-5 模块（占总面积 60% 以上时，只改它们）
2. 功耗 Top-5 网络（时钟树、宽总线、高翻转计数器）
3. 时序最差 10 条路径的公共段
4. 存储访问次数 Top-3 的数据流（影响带宽和功耗）

**改前 5% 拿 80% 收益**，剩下的属于打磨，收益递减且风险递增。

### 功耗报告怎么读（与面积报告同等重要，但常被跳过）

- **先看三块占比**：internal / switching / leakage。前两块合起来是动态，占比决定手段——internal 占大头查组合逻辑深度与毛刺，switching 占大头查翻转率高的总线与计数器。
- **时钟树单独看**：时钟网络功耗通常占总动态 20–40%。这一块 RTL 侧改不动（归后端），但 **clock gating 漏掉的寄存器组**能从这里看出来——某个模块时钟功耗异常高、又没有 ICG，就是 RTL 侧的活。
- **分层看**：按 hierarchy 从上往下钻，找 Top-5 实例而不是 Top-5 网络；实例对应模块名，修法才落得到代码上。
- **口径先确认**：向量集是真实应用还是 VCD 随机？时间窗口多长？没标口径的功耗数字没法和预算比——**报告里功耗比上一版涨 30%，先查是不是换了向量集，再查 RTL**。
- **每周期功耗（pJ/cycle）换算**：`P / f`，用来跟架构预算里的 `α·C·V²·f` 对账，两边口径不一致时先对齐 α（0→1 概率 vs toggle rate，见第 1 节）。


## 3. 手段与代价表

| 手段 | 省什么 | 代价 | 什么时候用 |
|---|---|---|---|
| Clock gating（ICG 单元） | 动态功耗 20–40% | 几乎无（加 ICG 面积） | 默认就该做 |
| Operand isolation | 组合逻辑翻转 | 加隔离逻辑 | 大位宽运算单元空转时 |
| 资源共享（分时复用） | 面积 20–50% | 吞吐降 / 需要仲裁 | 吞吐有余量时 |
| 位宽收敛 | 面积、功耗 | 精度或动态范围损失 | 先确认数据范围 |
| 拆大 mux 为两级 | 时序、可能省面积 | 多一级延迟 | 优先级链 >8 项 |
| 加流水 | 时序 | 面积 + 延迟 +1 拍 | 结构问题，主流解法 |
| 并行换频率 | 时序（降频后好收） | 面积近似线性增长、功耗上升 | 频率是硬指标时 |
| 状态编码改一热 | 时序（解码浅） | 触发器变多、功耗略升 | 状态少但转移复杂的 FSM |
| 存储器分 bank | 带宽 | 面积、控制复杂度 | bank 冲突是瓶颈时 |
| 门控/关断整块 | 静态功耗 | 唤醒延迟、需 isolation/retention | 有低功耗模式 |

## 4. 三角关系：动一个必动另一个

| 你想要的 | 通常要付 |
|---|---|
| 更快（频率↑） | 面积↑（流水/并行）、功耗↑ |
| 更小（面积↓） | 频率↓ 或 吞吐↓ 或 延迟↑ |
| 更省（功耗↓） | 频率↓ 或 面积↑（更多门控/隔离） |

**没有免费的优化。** 每次给建议都要同时写另外两项的变化方向和量级，否则就是没想清楚。

## 5. 优化建议的写法

```
结论：面积超 15% 主要来自 u_mac_array 的 16 个 MAC lane 全并行（占 42%）
手段：改为 8 lane × 2 时隙分时复用
收益：面积 -21%（估算），仍满足目标算力（利用率从 55% 升到 78%）
代价：延迟从 12 cycle 增到 19 cycle；控制逻辑增加约 3%（仲裁状态机 + 双缓冲）
风险：利用率假设依赖输入 tile 尺寸，小于 8×8 的 tile 会掉到 40%
回退：参数化 `LANE_NUM`，可从 8 改回 16，代码不用重写
```

四段缺一不可：**结论 / 手段 / 收益 / 代价与风险**，能参数化回退的加分。

## 6. 判断"优化到位"的标准

不是越小越好，是三点：

1. **达标**：面积、功耗、频率都在预算内
2. **可维护**：改动没有把代码变成不可读的状态；优化点有注释说明为什么这么写
3. **可回退**：关键优化做成参数或配置，能改回去

过度优化的典型症状：为了省 3% 面积写了难以理解的位拼接、把两个不相关的模块强行合并、用满所有时隙导致验证组合爆炸。这些成本不会出现在 PPA 报告里，但会在后端和验证阶段以更贵的形式出现。

## 7. 粗估公式（早期没有报告时用）

```
逻辑面积   ≈ gate count × 单位门面积（工艺库查）
触发器面积 ≈ FF 数 × 单位 FF 面积（通常是单位门的 4–8 倍）
SRAM 面积  ≈ bit 数 × 单 bit 面积（该节点、该 bank 配置下查表）
动态功耗   ≈ Σ(α_i · C_i) × V² × f      ; α_i 为 0→1 概率口径，C_i 含下游全部负载
```

**这些只能用来比方案之间的相对大小**，不能拿来说绝对面积。给绝对数字之前必须先要报告。
