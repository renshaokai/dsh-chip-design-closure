# 数字芯片前端设计工作底稿

这份技能不提供"标准答案"，提供的是**每一站交付物的形状**：架构方案该带哪些数字、规格该有哪些章节、RTL 该守哪些纪律、报告该怎么读、评审该逐条查什么。用它把"我觉得应该这样"变成"这里缺了这一项，按这个格式补"。

## 十六条硬规矩

1. **数字要有推导链**。任何带宽、周期、面积、功耗，必须能倒推回参数（频率、位宽、并行度、工艺）。只给结果不给公式的，等于没给。
2. **架构结论是一组解，不是一个方案**。面积/功耗/吞吐多目标下不存在唯一最优，直接拍三个方案来比等于用专家经验抽样——抽到的那三个点之间比出的"最优"，可能整个参数空间里都排不进前十。先定扫描维度与档位（并行度 / 频率 / 片上存储 / 复用粒度这四个主导，其余固定并标注），再用硬约束剪枝，最后对幸存者出 Pareto 前沿。**每个解必须标"被什么约束卡住"**，否则前沿只是一堆数字；前沿上所有解都被同一约束卡住时，优化方向就唯一了（去改接口，别再调阵列宽度）。解析模型误差 ±30%，只用于排序与剪枝，定案前必须对前沿上的点做一次综合或性能模型验证。见 `arch-budget.md` 3.1–3.4。
3. **契约先于实现**。寄存器表和接口表是设计与验证的共同事实，先定死再写 RTL。两张表对不上，先改表，别改代码去迁就。
4. **问题必须分级**。报告解读先分桶（必修 / 可豁免 / 工具误报 / 待确认），再给明细。不做分级的 400 条清单等于没读。
5. **缺口显式化，但不许留空**。定不了的事先给候选、标等级、指问题编号——**裸 `TBD` 不是交付**。危险程度三档：当事实写不标记（最危险，下游当契约用）＞ 留 `TBD` 空着（客户收到半份文档）＞ 给候选 + 标 `TBC`/`inferred` + 指 `[?Q-xx]`（唯一可接受）。反向场景尤其：客户把 RTL 交过来是要一份能评审的文档，留空等于把工作原样退回。见 `spec-outline.md` 5.2。
6. **文档粒度跟责任边界，不跟代码层级**。一个 IP 内部有几个子模块不构成拆文档的理由；RTL 里例化几十个 leaf module 也不构成 spec 拆到叶子的理由。拆的判据见 `spec-outline.md` §1.1 的四条（责任人 / 交付节奏 / 评审场合 / 版本演进），**两条以上成立才拆**；往下拆的判据三条：有独立契约、能独立验证、有独立寄存器或时钟域。
7. **spec 的效力来自写在前头**。同一份文本在实现之前是契约（实现服从文档、冲突走变更评审），在实现之后只是记录（文档服从实现）。如果它永远不可能和现实冲突，就没法用来检验现实是否正确。写 spec 时先问一句：这条断言，将来有没有可能被证明是错的？
8. **逆向文档必须标出处，且不许冒充契约**。从 RTL 反推的每一栏都要标 `measured` / `inferred` / `TBC`（`tbd` 已从内容行废除）。`measured` 只代表"取到的这部分是对的"，不代表没漏——覆盖不到的写法会静默漏掉并同样标成 measured。所以必须附已知限制与需人工复核清单。反推稿不能拿去当设计依据或应付评审，**但走完 5.8 的七条准入清单（评审只评事实/缺口/理由，签发冻结）后，对后续修改恢复契约身份**。
9. **止于 VP，不碰验证环境**。本技能只管设计侧：产出到功能点（FP）与验收观察点（VP）清单为止。TB、sequence、testcase、断言、coverage bin、跑仿真、覆盖率报告解析，全归验证侧。被问到这些，写清归属并给出交接接口（编号/分级/预期结果/观察点位置），不要顺着答下去。
10. **形式按内容选：有值用表，有关系用图，只有理由用散文**。散文每节 ≤3 句。**承载取值的图要配表**（波形图配「拍号/信号/期望值/前提」四列，时序/状态机/计算映射同理）；**只表达结构或拓扑的图不必配**——给每张图都造镜像表，等于两份数据手工同步，必然漂移。两头都要禁：用散文（或图）代替取值，追着图造复述表。见 `spec-outline.md` 总则 0.1–0.3。
11. **写在前头就横穷尽、纵到决策**。横向（功能、模式、异常路径、边界组合）无上限，应当穷尽；纵向写到影响他人的决策为止（流水级数、并行度、仲裁、精度、拍数），不写语句与风格。写得越细越要配偏离登记——只写不回写，详细就是负债。
12. **功能点从行为切，不从结构切**。一条 FP = 一个可独立判对错的外部可观察行为。反向反推时尤其容易错：按 module、always 块、寄存器字段去数，数出来是代码结构清单。三问过筛（外部可观察/实现无关/可独立判错），粒度报警线 10–40 条。见 `spec-outline.md` 5.7。
13. **名字只住在表里**。端口表、寄存器表、状态编码表用真实名（驱动与集成要照着写代码）；正文、图、功能表、决策台账一律概念名。允许出现代码的只有参数化位宽公式、位域拼接、状态编码值三处。正文里未解释的内部信号名超过 5 个，就不是文档而是代码的另一种排版。见 `spec-outline.md` 5.3.2。
14. **闭环完整性这一章不许裁**。前面几章各写各的，只有它能回答"有没有漏掉什么"：需求追溯矩阵（每条需求落到哪节、哪个模块、由哪些 VP 覆盖）、V 模型闭环检查表（每个环节的**验收方法是否先于实现定下来**）、未闭环清单（缺口可以写"无"，但不能不写）。**两条硬判据**：每条需求至少一个 VP，每个 VP 能倒查到需求——倒查不到的 VP 说明在验一个没人要求的行为，要么需求漏了，要么用例多余。判"环节已确认但验收方法未定"的一律记断点，不许写"后续补充"。见 `templates/spec-template.md` 第 7 章。
15. **时序描述按采样沿之后写，推断不许双写两种语气**。反向文档的 P0 错误几乎全出在这两处。① 状态与输出同沿更新时，外部看到的是"更新之后"的值——写成"done 在 STOP 态置高、下拍进 IDLE"会让读者以为二者同拍；判据是"这两个信号是否同一时钟沿赋值"。派生指示给递推式（`activity[n] = (state[n-1] != IDLE)`），不写"延迟 N 拍"。② 进了问题清单的项，正文必须同步降级并标 `[?Q-xx]`——清单说"待确认"、正文说"用于……"，读者只会信正文。附带两条：功能状态列只答"代码里有没有路径"（不写"已实现"）；关键时序契约给 `CPL-xx` 编号且只写一处。见 `spec-outline.md` 3.b / 附录 E、`templates/spec-template.md` 3.3.3 / 3.e。
16. **状态机交三张表，不是一张**。转移表回答"从哪到哪"、**状态×输出矩阵**回答"驻留时外部看到什么"、**不变量表 `INV-xx`** 回答"无论怎么跑都必须成立什么"。转移表必须有**判定顺序列**（代码里 `else-if` 的顺序就是优先级，是硬事实不是解释）与**显式的兜底行**（"保持本态"不许省——省掉之后读者不知道条件都不成立时会发生什么，那正是卡死类缺陷的藏身处）；输出矩阵必须 **Moore 与 Mealy 分开**（混排会让验证按 Moore 写断言而漏掉输入路径）；不变量只写**恒真、无需激励即可判**的项，与 VP（需激励看预期）严格分开。见 `spec-outline.md` 3.b、`templates/spec-template.md` 3.3.4。

## 全流程的交付节奏

```
需求 → [架构方案] → [设计规格] → [RTL] → [lint/CDC] → [综合] → [时序/PPA] → 集成 → 后端
         A 分支        B 分支      C 分支   D 分支       E 分支     F 分支      soc-integration
                        ↑
                   B′ 分支（已有 RTL 时反向回填）
                        ↓
                   B″ 分支（spec → FP/VP 交验证）
```

- **架构阶段**：结论 → 权衡表 → 预算数字 → 风险与前提。四段，别混。**权衡表是探索的结论而非起点**：先定扫描维度（并行度 / 频率 / 片上存储 / 复用粒度），再剪枝，再出 Pareto 前沿（每解标"被什么卡住"），最后从前沿挑点填权衡表。
- **规格阶段（正向）**：PRD 判读（有量化指标吗）→ 粒度决策 → 骨架 → 契约表 → 模块六要素（实现方式落到四要素+算子表+资源账+精度）→ 图（承载值的配表，结构图不配）→ 决策台账 → 可观测出口 → **逐条自查（`review-checklist.md` 第一节 66 条，机械项给结论、判断项给理由）→ 三个过程动作（散文占比 / 复述测试 / 审核者工作流测试）**。**先写文档再写 RTL**：RTL 阶段是"把文档翻译成电路"，所以文档是来源、代码是像，不是反过来。
- **规格阶段（反向）**：判可提取度 → 先抛开 RTL 列功能候选 → 三级筛定粒度 → 三类字段标出处 → **四类补不出的给候选标 `TBC`（不留裸 `TBD`）** → 八章骨架同正向、按档调填充 → 名字只住表里 → 问题清单（带默认判断与问题性质）→ `REQ-xxx` 候选 + 防冒用声明 → 6B 验证基线 → 双向倒查 → **逐条过 `review-checklist.md` 一·B 的 45 条**。**要交接档还是要归档档，先问清楚**——判据是"读完敢不敢改这段 RTL"；**收尾必须对账**——RTL 核对结果表（文档描述 / RTL 实际 / 结论）与文首评审摘要（五条固定），并核对问题清单与正文语气是否一致。
- **FP/VP 生成**：提条款 → 组 FP → 分级 → 设计 VP → 拆并 → 分子模块与顶层 → 查三条文档自洽断点 → 附基线声明。止于 VP。
- **验证交接（第 6 章）**：定范围与不验理由 → 标重点风险 → 落 FP/VP 清单 → 写基线声明 → 写明"本章不包含什么"。**这一章叫"验证方案"，写的是设计侧交给验证侧的输入，不是验证计划。** TB/sequence/断言/coverage bin/覆盖率目标/回归流程一律归验证侧。
- **RTL 阶段**：接口 → 控制/数据分离 → 边界处理 → 自检清单 → 待验点清单。
- **收敛阶段**：先查约束 → 违例分级 → 找公共根因 → 改法排序 → 收敛判据。
- **集成阶段**：地址表 → 接口参数 → 域图 → 中断表 → 低功耗件表。先定契约再接逻辑。
- **评审阶段**：逐条判定 + 位置定位 + 分级 + 修法。

## 一条贯穿全流程的原则

**上游的每个数字，下游都要能倒推回来。** 架构说"64 byte/cycle 带宽"，规格里要有对应的接口位宽与突发长度，RTL 里要有对应的数据通路宽度，综合后面积要能解释这 64 字节去了哪里。任何一环对不上，就是缺陷，不是"大概没问题"。

## 常见错误（评审现场会被点名的）

- **把文档类别当选择题丢给用户**："你要 IP 级还是模块级、架构级还是实现级？"——这些标签是方向（§1.3）、拆分（§1.1/§1.2）、深度（0.6 + 归档/交接档）三步推导完的**结果**，不是入口选项。先盘点手头资产（§1.0），缺什么就产出什么。
- **拿代码规模当拆分判据**："超 5 个模块或 5000 行就升级成 IP 规格"——行数与契约面相关但不因果，可当提示信号，不可当判据。
- **把抽象层次做成两套文档模板**："架构级一份、实现级一份"——层次是同一骨架的填充深度，做成两套必然产生两份手工同步的接口副本。
- **让用户先挑文档类别**："你要 IP 级还是模块级、架构级还是实现级？"——这些标签是方向（§1.3）、拆分（§1.1/§1.2）、深度（0.6 + 归档/交接档）推导完的**结果**。用户不会报资产清单，他会说"帮我看看这个模块"并甩个 `.sv`——**读他的话，不要读他填的表**。
- **一上来就盘问**："你的 PRD 在哪、有没有设计者可访谈、RTL 冻结了吗"——三连问是把分诊工作推回给用户。能推的先推（甩代码+没文档=反向；"我看不懂"=交接档；"驱动问我要寄存器"=摘录版），**只问推不出的三类**：交给谁验收、什么时候要、他自己懂不懂。
- **推定完不复述**：推了但不告诉用户推的是什么、依据什么、错了怎么改，他只能被动接受一个错误分类。固定三段：**结论 / 依据 / 退路**。
- **只在开头确认一次就一路写到底**：用户回一句"好的继续"，分类错了会错到交付，那时推翻等于重写。**必须在第一个里程碑自检一次**（正向：骨架+前两三章；反向：问题清单+功能表候选），问"深浅和用途对不对"，不要问"这样写行不行"——后者只会换来一声"行"。只问这一处，别每章都问。
- **只有想法没有 PRD 就往 B 里塞**：B 的输入是 PRD，没有就写不出第 2 章。这种该进 A 分支先出架构方案。
- 预算数字手填常量，改了并行度表就不自洽。
- **拿 MRD 当 spec 的输入**：MRD 只回答"值不值得做"，功能清单、指标、验收判据都在 PRD 里。用 MRD 写出来的第 2 章只有场景描写。
- **PRD 只给功能清单、不给量化指标就开写**：P0/P1/P2 的判据是"缺了它能不能用"，没有吞吐/延迟/功耗数字就只剩经验值。缺指标要进缺口表并说明 FP 分级失去依据。
- 架构决策只写结论不写"为什么不选另一个"。
- 寄存器表只写地址不写位域属性与复位值，验证无法建模型。
- 接口表位宽写 `N` 或 `N/8`，实际无法比对。
- 状态机只画主流程，漏 `ERR → IDLE`，图不闭环。
- **多模块 IP 的寄存器表每段都从 0x000 起写**：看着整齐，驱动要自己拼地址，且机器无法判段冲突。必须用绝对地址 + 段分配表。
- **把多个子模块 spec 按模块分章装订成"系统级 spec"**：读者问"启动时序怎么走"要翻遍每一章。系统级只写跨模块的事（拓扑、契约矩阵、时钟复位、地址映射、跨模块场景）。
- **spec 拆到 RTL 叶子模块**：写 8 位移位寄存器进 spec，等于替设计者做实现选择，还白占篇幅。拆到契约能冻结的那一层就停。
- **把 as-built 文档当设计规格交付**：RTL 先存在，文档只能描述它，永远约束不了它。评审要的是实现之前的契约，事后补的没有信息增量，只是 RTL 的另一种排版。
- **逆向文档里出现没有出处标记的断言**：读者无法判断哪句能引用、哪句是推断。推断当事实用，比留空危险得多。
- **看到"寄存器数 0"就写"本 IP 无寄存器"**：可能是译码写在宏或 generate 里、或地址选择信号命名不带 addr。零结果要先排除提取失效。
- RTL 里参数化位宽在顶层被字面量写死。
- 多 bit 跨时钟域只做两级同步，没走格雷码或异步 FIFO。
- 复位释放不同步，异步复位同步释放只写了一半。
- **见 warn 就改**：lint 400 条一条条改，引入的风险大于收益。
- **清零式收敛**：全设 false path、全标 waiver，报告干净了芯片是坏的。
- **靠提高综合 effort 收时序**：只能榨几个百分点，结构问题必须改结构。
- **多周期只写 setup 不写 hold**：工具的 hold 检查点跟着往后挪，比真实要求更宽松，硅上出错而报告干净。必须成对写。
- **地址空洞没 default slave**：读到没接的地址总线永不回，表现为随机死机。
- **outstanding 拍脑袋**：带宽只有理论值的几分之一，而所有报告都正常。
- **属性值凭经验填**：寄存器表 attr/reset 看着合理，源码里读不出写清路径，验证建模型时就对不上。
- **端口在、逻辑不在**：信号声明了却从未被引用，文档按名字当成能用——必须标未参与功能并进附录 E。
- **反向 spec 夸能力**：只有参数声明或 generate 框架就标"路径存在"，集成方按此设计后发现通路不存在。
- **推导值当保证值**：把"最多 8 拍"直接给下游，前提一改就错位；文中必须同句标推导与前提。
- **双向混写**：一份文档里一半写设计意图、一半记代码现状，读者分不清哪句是承诺。要么标明分节，要么分成两份。
- **正向 spec 写成实现说明书**：把"打算怎么做"写成"当前代码怎么写的"，等于把未定方案锁死，评审时无法再改。
- **自证闭环**：反向 spec 的 VP 预期取自 RTL，验证按此检查等于用实现验证实现，缺陷被写成"预期行为"永久通过。必须引入需求侧来源与设计者确认，并写明能力边界。
- **FP 按字段数去数**：一个寄存器位域一个 FP，得到的是字段清单不是功能点，验证按它做出来覆盖不到行为组合。
- **验证不分级**：P0/P1/P2 不分就直接排用例，最后边界磨得很细而基础路径有洞，覆盖率数字还很好看。
- **把验证环境揽过来**：顺着"覆盖率缺口"往下做 TB、写 sequence、解析报告。设计侧产出止于 VP 清单，再往下是验证侧的活——越界的结果是两头都没做好，还让验证方以为缺口已有人管。
- **第 6 章写成验证计划**：写 UVM 环境结构、覆盖率目标百分比、回归流程——那是验证方的《验证计划》，设计者写不了也不该签。第 6 章只写范围边界、风险提示、FP/VP 清单、基线声明。
- **spec 版本漂移**：RTL ECO 后 spec 不跟着更新，验证拿旧基线测新代码——报告全绿，测的不是当前实现。ECO 后必须增量回填，并把预期值失效的 VP 标出来通知验证方。
- **同一份 spec 手写多份格式**：md 一份、Word 一份，第一个 ECO 后就分叉。Markdown 是唯一可编辑源，Word/PDF 是生成物；评审批注收回来改源再重新生成。见 `delivery-formats.md`。
- **Markdown 里贴截图不贴图源**：图变成不可追溯的位图，改模块名图不跟着变。图源（.drawio/.mmd/.wavedrom）进仓库，Word/PDF 里的图由源渲染生成。
- **以为写了 DSL 块就等于图出来了**：Markdown 平台能渲染 mermaid，但 Word 只会把代码块原样印成文本。交付前必须跑 `figrender.py` + `md2doc.py`，并在 Word 里翻一遍确认每张图都在——**这是最容易漏检的一处，因为正文看起来"有内容"**。
- **拿 Mermaid 画架构框图**：`subgraph` 只要跨组有连线（SoC 图必然有），嵌套就失效、子图被甩出父容器。架构图用 draw.io 手写 XML，位置才可控。
- **把画图推给人工或指望 MCP**：`.drawio` 是 XML，AI 直接写；MCP 的产物是浏览器里的一次性会话，进不了仓库、不能 diff。交付链路要的是文件 + CLI 导出。
- **图跑出来了没看就往下走**：走线穿方块、子图出界、标签压线，退出码全是 0。架构图出完必须开一眼。
- **改了图源不重渲染**：文档里还是旧图，Word 看不出异常。`md2doc.py` 的 `[过期]` 警告就是这件事，别忽略。
- **交付不给图源**：只给 docx/pdf，用户想改一个字都改不了。`fig/` 目录要一起给，并说明哪份可改。
- **把 SVG 直接塞进 Word**：python-docx 不认 SVG，抛 `UnrecognizedImageError`。Word 一律用 PNG（`figrender.py` 默认出，md2doc 会自动换）。
- **「实现方式」写成一句话**：写"采用三级流水、片内 SRAM 缓存"就算完——数据怎么传输、算子映射到什么资源、复用几次、溢出怎么处理全没有，验证给不出预期值，主管也判不出方案好坏。
- **精度口径不写**：算法侧说 INT8 累加，硬件用 32 位还是 24 位、饱和还是回绕不写，验证只能猜；猜错的方向总是"两边都自认为对"。
- **传输只写路径不写生命周期**：进了 buffer 没人写谁释放，credit 只借不还——功能全对，带宽慢慢掉下去，集成期最难查。
- **状态机只有跳转表没有跳转原理**：表永远自洽，可"为什么拆成这几个状态、为什么不合并"没人写，划分合不合理无从判断，而这正是主管该判的那一层。
- **决策只记结论不记失效条件**：三个月后没人敢动，六个月后没人记得为什么。
- **内部状态没有可观测出口**：硅上出问题调不出来，只能靠猜；验证找不到观察点就会去驱动内部信号。必须给映射表，并写明哪些"看不见"。
- **散文写契约**："适当的时候反压""较快""若干拍"——读着通顺，一处都核对不了。这类词挑干净，比通读三遍有效。
- **详细但不回写偏离**：文档停在 v1.0 而 RTL 已经改了三轮，验证照它写用例会在正确的代码上失败。**陈旧文档比没有文档更危险**——新人以为自己知道。
- **写到语句层**：把 `if (cnt == 4'd7)`、三段式还是两段式写进 spec，评审变成读代码，且必然漂移。纵向止于决策层。
- **把上一份文档的个案例子搬进规则**：规则条文本身是通用的，但示例里带着某个模块的真实信号名（`mst_xxx`、`tx_xxx`、`ic_xxx` 这类前缀）、某个状态机的状态名、某条特定假设——**换个项目就变成误导，还会泄漏上一家的设计信息**。示例一律用**角色名**（"对端握手响应""完成信号""存储读接口"）+ 时序关系写，不用真实信号名；确实需要具体名字时，用 `foo`/`bar`/`sig_a` 这种明确无意义的占位。判据：把这条规则给一个完全不同的模块看，示例还成立吗。
- **根规矩改了，散落章节没跟上**：全库正文都改成了新规矩，但**输出规范、自检清单、模板使用说明**里还留着旧词——这三处比正文更危险，因为它们是每次回答都会读到的地方。典型症状：正文写"`TBD` 零命中"，输出规范写"未定项标 `TBD`"；正文写"给候选"，模板写"三种替代"却把 `TBD` 算作一种。**自查方法**：把被废除的旧词全库 `grep` 一遍，不看命中数量，**逐处看语气是"禁止"还是"允许"**——命中在"禁止"句式里是安全的（元描述），命中在"允许/应当"句式里就是没改干净。判据：这个旧词如果照着做，会产出你刚刚禁止的那种文档吗。
- **同一套检查写了两份，然后各自漂移**：`spec-outline` 5.4 有一份 26 条自查，`review-checklist` 一·B 有一份 29 条专项，**看着像重复，实际两边都有对方没有的**（7 条重复、18 条只在 5.4 里）。这种"两份都像对的"最难查——agent 读到哪份就按哪份查，结果取决于它先打开了哪个文件。**规矩：一份清单只能有一个物理位置**，其余地方只写引用与分工（"契约正确性归清单，写作过程项归本节"）。判据：如果把两份合并，会不会丢掉条目？会，就说明它们不是重复而是漏同步。
- **只给难题做检查，更容易的题就没人管**：反向档因为难，从 v1.6 起就有 26 条专项自查；正向档因为看着顺手，写完后只有 5 项自检，实测覆盖清单 11%。**这是评审设计上的双标，而且方向反了**——正向文档的错误更贵，它会被下游当需求基线，反推稿至少还带着"As-Built"的免责标签。给任何流程加检查时先问：**正反两个方向是不是都加了，还是只加在了出过问题的那一边**。判据：如果这次的自检清单被执行，产出的文档能过评审吗——不能，就是清单本身不够。
