**三条形式硬规矩**（详见 `spec-outline.md` 总则）：

1. **表必带前提**——行外假设写在表头或表上方，不散进正文段落
2. **承载取值的图配表，纯结构图不必配**——判据是"这张图能不能被指着说这里错了"。时序 / 波形 / 状态机转移 / 计算映射四类必须有表（波形图配「拍号 / 信号 / 期望值 / 前提」四列）；结构图、拓扑图本身已是完整信息，配表容易变成复述方框，反而制造两份要同步维护的数据
3. **散文 ≤3 句且只写"为什么"**——要禁的是两头：用散文（或图）代替取值（"适当的时候反压""见图 3 便知"），以及追着图造复述表。散文少不等于合格，可能只是把该讲理由的地方砍成了表。

**规范性动词约定**（混用会让读者不知道哪句要遵守）：

| 动词 | 效力 | 用在哪 |
|---|---|---|
| **必须 / 不得 / 禁止** | 规范 | 契约条款、约束、接口要求。实现不符即缺陷 |
| **应 / 不应** | 规范，允许有理由偏离 | 默认做法。偏离须在 3.c 登记理由与失效条件 |
| **可 / 可以** | 非规范 | 实现自由度、可选优化 |
| **说明 / 示例 / 推断** | 非规范 | 解释、举例、候选。不得被引用为要求 |

两条纪律：**一条契约只用一个动词，不叠用**（"应必须"等于没写）；**非规范内容必须显式标注**（标题加"（说明）"、表格上方加"以下为推断，非要求"）。反向档整篇默认非规范——它是记录，不是要求。

**必备标记**：每节标题后的 `[必填]` / `[按需]` / `[待填]` 是填写前的自检位，交付前**全部清掉**。

**内容里不许出现裸 `TBD`——这是反向档的硬规矩。** 客户把 RTL 交过来，要的是"你替我抽象出来、我们能拿它评审"，不是一份"这里我不知道"的清单。四种做法里只有最后一种算交付：

| 做法 | 后果 |
|---|---|
| 当事实写、不标记 | **最危险**：下游当契约用，错了无声 |
| 留空 / 留 `TBD` | **不算交付**：客户收到的是半份文档，工作被退回 |
| 给候选 + 标 `TBC` / `inferred` + 指 `[?Q-xx]` | 可评审：审阅人一句话即可确认或否定 |

**`TBD` 零出现**（不是"局部允许"）。写不下去时只有三种替代，都不含 `TBD` 字样：`本模块不适用`（给理由）/ `TBC－见 Q-07`（候选已给、待确认）/ `由 XX 文档给出`（该项不归本文档，如频率由 SoC 约束给出——**写明是哪份**，不许只写"见文档"）。**自检时对 `TBD` 应零命中**（模板使用说明与规则条文里的引用除外）。

**图的编号**：`图 3-A-02`＝第 3 章 / 模块 A / 第 2 张。表的编号：`表 4-B-01`＝第 4 章 / 模块 B / 第 1 张。多文档并存时没有编号无法沟通。

### 3.3.3 时序契约

**单时钟域**（标题注明 `（aclk 单域）`）：

| 编号 | 路径 / 场景 | 拍数 | 级别 | 前提 |
|---|---|---|---|---|
| CPL-01 | | | M / R / X | |

**多时钟域时按域分小节**（不要为形式拆，单域就写一节）：

- `3.3.3.1 aclk 域`：本域内拍数、反压传播、流水深度
- `3.3.3.2 mclk 域`
- `3.3.3.3 跨域路径`：逐条写 源域 / 目的域 / 信号宽度 / 同步方案 / 数据一致性要求

> **多 bit 信号不允许"各自两级同步"**，必须走格雷码、异步 FIFO 或握手。单列这一节就是为了让这个判断有地方落笔。
> 拍数标 M/R/X：写进过性能预算或对外承诺的标 **M**（验证须写断言），只是设计时大致节奏的标 **R**。

**三条写法纪律**（反向文档出错率最高的三处）：

1. **同一契约只写一处**。完成位、脉冲宽度、清除优先级这类被多章引用的契约，用 `CPL-xx` 编号，正文其他位置（功能表、状态机、3.d、VP、附录）只引用编号。同一行为散在六处，改一处漏五处是迟早的事。
2. **外部可见行为按采样沿之后写**。状态与输出同沿更新时，外部看到的是更新之后的值。写成"done 在 STOP 态置高、下拍进 IDLE"，读者会理解成 done 与 STOP 同拍——正确写法是"done 的前置握手被采样后，下一拍状态变 IDLE 且 done 为高，再下一拍清零"。**判据：这两个信号是同一时钟沿赋值的吗。**
3. **派生指示给递推式**。`activity[n] = (state[n-1] != IDLE)` 一句话覆盖高电平窗口、启动边界、停止边界与对使能判断的影响；"有 1 拍延迟"写四处仍是四处漏定义。

### 3.3.4 状态机

**（1）状态编码表**

| 状态 | 编码 | 驻留性质 | 进入条件 | 离开条件 |
|---|---|---|---|---|
| | | 单拍 / 多拍 / 自环 | | |

> **驻留性质**这一列看着多余，其实决定了后面所有时序纪律：标"单拍"的状态不允许连续出现两拍（见本节 (4) INV），标"自环"的状态才是真正会等的那个，性能瓶颈只可能在这里。

**（2）状态转移表（带判定顺序）**

| 当前状态 | 判定顺序 | 转移条件 | 下一状态 | 优先级 |
|---|---|---|---|---|
| | 1 | | | 最高 |
| | 2 | | | |
| | 3 | | 保持本态 | 兜底 |

> **判定顺序是硬事实，不是解释。** 状态寄存器是一条 `else-if` 链，顺序就是优先级——同一拍多个条件成立时，谁赢由这个序号决定，与"哪个更合理"无关。把它塞进散文写"优先处理 A"，读者无法据此推出多条件同拍的唯一结果。
>
> **兜底的"保持本态"必须显式列成最后一行**，不能省——省掉之后读者不知道"条件都不成立"时会发生什么，而这恰好是无响应类缺陷的藏身处。

**（3）状态 × 输出矩阵（Moore / Mealy 分开）**

| 状态 | 输出1 | 输出2 | 输出3 | … |
|---|---|---|---|---|
| | 电平 / 单拍 / 组合相关 | | | |

> **这张表按"状态"组织，不按"转移"组织。** 转移表只能说明跳到哪里，说明不了"处在这个状态时外部看到什么"。反向文档最容易犯的错就是只列转移、不列驻留输出——读者于是只能从"某条转移发生时置了某位"倒推，倒推出来的同拍关系经常是错的（见 3.3.3 纪律 2）。
>
> **Mealy 输出单列一栏或在格内标注 `(Mealy: 依赖 XX 条件)`**，不要和 Moore 混在一格里：Moore 输出只看状态，Mealy 输出同时看输入，两者的时序属性完全不同，混排会让验证侧按 Moore 写断言而漏掉输入路径。

**（4）状态机不变量（INV-xxx）**

| 编号 | 不变量 | 为什么必须成立 | 归属 |
|---|---|---|---|
| INV-01 | | | 架构 / 微架构 / 接口 |

> **不变量是恒真声明，不需要激励就能检查**——这跟 VP 正相反：VP 要"给激励、看预期"，INV 是"无论怎么跑都必须成立"。所以两者不能合并：INV 适合放"某状态不得连续驻留超过 1 拍""某两态互斥""某输出不得在复位期间为高""指针不回绕条件下的计数不越界"这类；VP 适合放"给一次完整传输，看到 done 宽度恰 1 拍"。
>
> **每条不变量都要能说出"为什么"**——写不出理由的，多半是描述了一个实现细节而不是真不变量，会随改版立刻失效。

**（5）闭环检查**：任意状态可达 IDLE；无死路；有 `ERR → IDLE`；复位值明确。

> 跳转表永远自洽，划分是否合理只能靠这几句判断。**主管评审看的正是这一层。**

### 7.1.1 反向档：需求候选与矩阵标注 `[反向必填]`

RTL 里没有需求来源，但**不构成不写这一章的理由**——写出来的候选正是这次交付最值钱的部分：客户拿它对照原 PRD，一句话就能确认或否掉。

**第一步：先把需求候选造出来。**

| 需求编号 | 反推出的行为描述 | 证据（实现位置） | 状态 | 关联问题 |
|---|---|---|---|---|
| REQ-001 | | 文件:行 / 状态机名 | `TBC` / `inferred` / `已确认` | Q-xx |

- **编号从 `REQ-001` 起，不复用客户 PRD 编号**——复用会让人误以为这条需求出自 PRD
- **描述只写"实现表现出的行为"**，不写"设计者意图"；意图不明确的追加 `[?Q-xx]`
- **状态三档**：`TBC`（候选，待客户确认）/ `inferred`（从代码强推，仍无书面确认）/ `已确认`（客户书面回复过，注明日期）
- **一条需求都造不出来是异常信号**，不是"本模块无需求"——通常说明功能表切分错了（见 agent B′ 第 5 步）

**第二步：文首必须加防冒用声明。** 放在证据状态声明之后，一字不改地写：

> 本章需求条目由 RTL 实现反推得出，**不是客户原始需求**。与客户 PRD 冲突时以 PRD 为准；本表仅用于建立"实现 ↔ 验收"的可追溯关系，不得作为需求基线引用。

**第三步：追溯矩阵照常填，未确认项标 `TBC` 而不是删行。** 反向档的五列都填得出来——需求编号用 `REQ-xxx`，落点用实际模块名，VP 覆盖用 6B 的清单。**唯一填不出的是"需求描述是否与客户本意一致"，那一列标 `TBC` 并在关联问题里指向 `Q-xx`。**

**第四步：如果所有行都是 `TBC`，这一节的标题必须改。** 改法：

> `## 7.1 需求追溯矩阵（评审议程 —— 尚未建立追溯）`

并加一句说明：

> 本表当前全部条目待确认，**不构成追溯矩阵，而是待客户确认的评审议程**。追溯关系在至少一条 `REQ` 被确认后建立。

**为什么要改标题而不是只标 `TBC`**：标题是读者判断"这段能不能引用"的第一依据。写着"追溯矩阵"、内容全是 `TBC`，下游会当成已建立追溯——这与"清单说待确认、正文说确定"是同一种病，只是换了位置。**声明必须出现在读者犯错之前。**

## 7.2 V 模型闭环检查表 `[必填]`

自上而下每一环都要有确认动作与结论，**没有确认动作的那一环就是断点**。这一条比追溯矩阵更进一步：它查的是"每一段的验收方法本身有没有定下来"。

| 检查环节 | 确认动作（谁来、以什么形式） | 结论 | 断点说明 |
|---|---|---|---|
| 应用场景已理解并确认 | | 通过 / 断点 | |
| 需求已拆解为规格条目 | | | |
| 整体验收方法已确定 | | | |
| 方案已确认 | | | |
| 方案验收方法已确定 | | | |
| 详细设计已确认 | | | |
| 详细设计验收方法已确定 | | | |
| 可测性要求已提出 | | | |

**判据是"验收方法是否先于实现定下来"**：先定验收再做设计，是 V 模型；做完再想怎么验，是倒推，通常验不全。凡是"方案已确认但方案验收方法未定"的行，结论一律写断点，不要写"后续补充"。

> **反向档八行通常是全断点，这不算失败，算如实登记。** RTL 已经写完，前四环（应用场景、需求拆解、整体验收、方案确认）**在时间上就不可能"先于实现"**。写在这是为了让客户看清断在哪一环、要不要补——**不是让你把断点写成"通过"来凑一份漂亮的闭环表**。整表全断点且如实标注的反向文档，比半真半假的闭环表有用得多。

**必须登记的四类（RTL 侧未明确）**：

1. 未被消费的端口或寄存器——存在但不参与功能
