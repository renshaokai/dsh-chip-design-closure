| 多模块 IP | 照本文档全用，3.3 按模块复制为 3.3 / 3.4 …；**3.c、3.d 用字母编号，是跨模块通用节，不参与模块复制，仍只留一份** |

**三条形式硬规矩**（详见 `spec-outline.md` 总则）：

1. **表必带前提**——行外假设写在表头或表上方，不散进正文段落
2. **承载取值的图配表，纯结构图不必配**——判据是"这张图能不能被指着说这里错了"。时序 / 波形 / 状态机转移 / 计算映射四类必须有表（波形图配「拍号 / 信号 / 期望值 / 前提」四列）；结构图、拓扑图本身已是完整信息，配表容易变成复述方框，反而制造两份要同步维护的数据
3. **散文 ≤3 句且只写"为什么"**——要禁的是两头：用散文（或图）代替取值（"适当的时候反压""见图 3 便知"），以及追着图造复述表。散文少不等于合格，可能只是把该讲理由的地方砍成了表。

**必备标记**：每节标题后的 `[必填]` / `[按需]` / `[TBD]` 是填写前的自检位，交付前全部清掉。

# 7 闭环完整性 `[必填]`

> **这一章不许裁。** 前面六章各写各的，只有这一章能把「需求 → 规格 → 实现 → 验证」四段串成一条链。缺了它，读者无法判断哪条需求已经落地、哪条在传递中掉了。**它是唯一能回答"我们有没有漏掉什么"的章。**

## 7.1 需求追溯矩阵 `[必填]`

一条需求一行，五列缺一不可。**"落到哪"与"怎么验"必须能点开看**，写"见第 3 章"无效。

| 需求编号 | 需求描述（一句） | 落到规格哪节 | 落到实现哪个模块 | 由哪些 VP 覆盖 |
|---|---|---|---|---|
| PRD-01 | | 2.2 / 3.1 | | |

**三条判据**（缺一条就说明链路断了，不是"待补"）：

- 每行都有**至少一个** VP 覆盖；没有 VP 的需求，要么不该进范围（写明为什么不做），要么是缺口（写进 7.3）
- 每个 VP 都能倒查到需求；倒查不到的 VP 说明在验一个没人要求的行为，**要么需求漏了，要么用例多余**
- 「落到实现」写模块名，不写"已实现"

## 7.2 V 模型闭环检查表 `[必填]`

自上而下每一环都要有确认动作与结论，**没有确认动作的那一环就是断点**。这一条比追溯矩阵更进一步：它查的是"每一段的验收方法本身有没有定下来"。

| 检查环节 | 确认动作（谁来、以什么形式） | 结论 | 断点说明 |
|---|---|---|---|
| 应用场景已理解并确认 | | 通过 / 断点 | |
| 需求已拆解为规格条目 | | | |
| 整体验收方法已确定 | | | |
| 方案已确认 | | | |
| 方案验收方法已确定 | | | |
| 详细设计已确认 | | | |
| 详细设计验收方法已确定 | | | |
| 可测性要求已提出 | | | |

**判据是"验收方法是否先于实现定下来"**：先定验收再做设计，是 V 模型；做完再想怎么验，是倒推，通常验不全。凡是"方案已确认但方案验收方法未定"的行，结论一律写断点，不要写"后续补充"。

## 7.3 未闭环清单 `[必填，可以写"无"]`

矩阵里查出来的缺口，逐条登记。**空着不写等于宣称全部闭环**，这是评审最容易抓的一处。

| 缺口 | 类型 | 影响 | 谁负责 | 计划 |
|---|---|---|---|---|
| | 需求无 VP / VP 无需求 / 环节未确认 / 明确不做 | | | |

标"明确不做"的也要登记理由——**决定不做，和忘了做，在文档里必须能区分开**。
